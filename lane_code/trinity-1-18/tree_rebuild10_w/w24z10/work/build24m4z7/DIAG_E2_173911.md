# E2 job 173911: diagnosis and tested diagnostic fix

**The saved evidence does not identify the real upload error.** It does identify why the error disappeared: `pc.py` redirects both writer streams to `/dev/null`, and E2 omits the copier state files that retain its return code. A strict offline protocol run passes all 14 checks with 16 receipts. Claiming a proven Content-Range, session-format, or TLS root cause would exceed the evidence.

The leading hypothesis is a fast, shared failure in the writer, most plausibly a session/HTTP rejection. TLS or interpreter/runtime failure remains a close alternative. No HTTP status, writer exception, runtime version, or cached session survives from job 173911, so this ordering is provisional. The patch fixes the confirmed diagnostic loss and an independently reproduced observer problem; it is **not a verified repair of the unknown remote failure**.

**Confirmed secondary observer defect:** under a spawn context, the supplied observer produced four receipts but zero captured responses. Fork produced four of each. Fresh spawned workers import gc.py without the parent’s HTTPS monkeypatch. This can explain response_fields failure, but **cannot by itself explain the real job’s absent receipts**. Evidence: `out/diag_173911/start_methods_checked.json` and its two `mp_checked_*/output.log` files.

`gc.py` uses **http.client**, not urllib or curl. It uses Python/OpenSSL default certificate verification and does not automatically use HTTP(S)_PROXY; urllib.request in the mint helper and curl can have different proxy/trust behavior. `-I` isolates Python import/environment startup, but does not erase TLS environment variables. HOME is not consulted for the default session path, though a nonisolated interpreter can consult user-site startup. The follow-up probe does not establish that all these settings matched the writer.

Additional silent exits are visible in the source: unsupported URL/netloc details after superficial URL validation; missing or unreadable local archives; short reads; JSON errors in an existing receipt file (`gc.py:57–64,84`); MD5 construction rejected by a restrictive crypto policy (`23`, before the upload try block); worker submission/serialization errors; malformed or incomplete response bodies; and generation/offset/SHA failures after a receipt (`pc.py:365–379`). A crash after remote completion but before receipt persistence permits an attempted replay of a consumed session. The writer skips prior receipts by size and offset rather than content hash (`85`), so stale receipts require separate care; this fresh-job report provides no evidence of them. These are code-path possibilities, not observed failures in job 173911.

The original forkserver experiment returned `E2_CHILD_FAIL PermissionError` before receipts in this restricted environment. It is not evidence that Orchard failed the same way. Its first adapter also overwrote the observer during fork/spawn execution; those observation counts are not used. `start_methods_checked.py` corrects that test boundary. The final proposed observer uses threads and passes all three configured contexts without starting a forkserver. No cluster-killed job was retried.

## Strict sink and the Content-Range hypothesis

`out/diag_173911/strict_sink.py` replaces the header-blind sink in `work/build24m4z4/e2_verified.py:34–48`. It checks method, byte count, range syntax/offset/total, nonfinal 256 KiB alignment, completion, consumed sessions, 308 Range acknowledgments, status queries, create-only conflict injection, final JSON size/MD5/generation and real CRC32C. Session state persists across worker processes with file locks. It models the relevant upload contract, not Google authentication, TLS or service availability.

**Content-Range is necessary for explicit multi-request chunks; it is not universally required for a single-request upload.** Each of the four part objects here is an independent one-request upload. Small final objects need not be multiples of 256 KiB. `conn.send` calls do not create HTTP requests. The absence of an initial X-Upload-Content-Length does not, by itself, make the later single-request Content-Length form invalid.

Protocol reference for operator review: [Cloud Storage resumable uploads](https://cloud.google.com/storage/docs/performing-resumable-uploads). This page was **not fetched** because this task forbids network access. The test explicitly distinguishes the standard single-request form from a deliberately stronger range-required policy; it does not present a local policy rejection as an observed Google response.

## Exact proposed fix and scope

`out/FIX_E2_173911.patch` changes **E2’s own `out/e2/observe.py` and `out/e2/e2.py` only**. Review copies are under `out/diag_173911/proposed/`. It does not change any of the four kit files `b/o.py`, `b/pc.py`, `b/pc.sh`, `k/y.json`, or the separate writer `b/gc.py`.

- Replace `out/e2/observe.py:11–43` with the proposed structured observer. Proposed lines 34–51 retain child starts/exits and preserve `-I -s` when inserting the observer. Lines 52–73 select up to four upload threads, record effective interpreter flags/version, executor, trust-path presence and a nonsecret object-key hash, and retain classified gc.py stderr. Lines 74–116 retain request IDs, lengths/ranges, connect/read exception classes, and every returned HTTP status, while forwarding the response bytes unchanged.
- At `out/e2/e2.py:78`, assert that the tmpfs session copy equals its node-local source and save only equality, byte count and key count (proposed 86–87).
- Extend `out/e2/e2.py:176–187` to retain the copier’s state files and final order, the structured writer log and session-copy record, and a manifest mapping archive members to local log sources. Continue including receipts without their local file path. Proposed code is at `proposed/e2.py:185–213`. The structured upload log is retained in full; other diagnostics retain their last 32 KiB. The final compressed archive still must fit the existing 2 MB limit. Proposed lines 69–76 also record the effective executable, runtime, local free bytes/inodes, resource limits, and configured timeout budgets. Lines 198–209 retain response metadata through a strict field allowlist, including when no part receipt exists.

This is an exact fix for **lost evidence**, child isolation loss, and observer portability. It does not pretend to fix an unobserved remote error. Adding Content-Range alone is not supported as the job’s repair. If a real 308 is captured, the writer needs an actual status-query/Range-offset continuation design with stable bytes and total size; blindly retrying byte zero is insufficient. That would change **b/gc.py, outside the four-file kit change**, and requires separate interrupted-upload tests. A 412 instead calls for checking the intended object/session allocation, not disabling create-only protection. A TLS failure calls for fixing the effective runtime/trust configuration, not disabling verification.

The patch remains unapplied to delivery files. Applying it changes E2’s pinned files, so E2 pin hashes must be refreshed by the delivery owner before any later real job; otherwise stage rejects them at E03. No pins, kits or upload packages were rebuilt here.

## What the next real-session job must keep

Keep these node-local diagnostics **inside logs.tgz before teardown**, even when no receipt exists:

1. Classified gc.py stderr: exception class, errno when available, HTTP status, and a nonsecret object-key tag. Keep body text, URLs, query strings, tokens, Authorization and session-map values out of the log. The patch extracts fields before persistence instead of deleting the only informative line afterward.
2. Per-request HTTP events: request ID, upload-worker PID, content length, Content-Range if sent, response status, validated numeric Range acknowledgment, and transport exception class if no response arrives. The patch emits these independently of gc.py’s redirected stdout/stderr.

Effective Python version/executable identity, isolation/user-site flags, multiprocessing setting/executor, OpenSSL version, CA-path presence/override flags, local free bytes/inodes, and remaining finalization budget. ## Lane finding 22:51Z (real GCS, binding for 24m4z7)
Root cause of 173911 is the e2 harness, not the kit: `out/e2/observe.py` (and the first tgcs observe.py) replaces `http.client.HTTPSConnection` with a subclass; http.client's own `HTTPSConnection.__init__` calls `super(HTTPSConnection, self).__init__(host, port, timeout, source_address, ...)`, which then resolves to the original HTTPSConnection.__init__ and raises `TypeError: HTTPSConnection.__init__() takes from 2 to 3 positional arguments but 5 positional arguments (and 1 keyword-only argument) were given` on every part (Python 3.12; Orchard has 3.12.3). Fail-before: W/work/tgcs_900001/logs/gc.stderr (sealed 24m4z4 kit_n, real sessions 900001, 0 receipts). Pass-after with the observer patching `HTTPSConnection.getresponse` on the original class instead (W/work/tgcs2/observe.py): W/work/tgcs_900001b: 16 receipts (ck00, m100, ckstop, o; 4 parts each), every HTTP 200, gc.stderr empty, kit gc.py unchanged (8d9fcaa1). So: fix e3's observer the same way (never replace a stdlib class with a subclass), keep gc.py as is unless another reason exists, and make the strict sink test also run through the observer.
