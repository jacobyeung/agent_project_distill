CANARY c — Tree C requires four ranks; its one-GPU admission performs no-grad forward, and smoke mode suppresses checkpoint/export.

Neither a helper inside discovery nor a separate one-GPU job can run the requested three optimizer steps unchanged. Reusing staging saves input work but does not remove the native world-size checks. No GPU job was run for this report.

Discovery already requests `weights=true`, `device=cuda:0`, memory_gib180. Its path is the decoded `k/j.json` shell → `b/a.py q` → `launch_r1.production_proof.run/_run` → native preparation and handover → `production_proof.forward` → `carrier_c1_run.first_batch_check` → `check_plan_rows`. `first_batch_check` loads the full model, casts base tensors to BF16, calls `.eval()`, and `check_plan_rows` uses `torch.no_grad()` (`carrier_c1_run.py:3039,3147–3151`). It checks one complete four-rank step's rows serially on cuda:0. This is useful encoding/forward evidence, not backward/Adam/checkpoint/export evidence.

The exact discovery config differs from N in two fields: proof_mode=q and init_policy absent. It uses absolute_resume_step400, so its forward proof selects the step after400 (`production_proof.py:164–175`, `carrier_c1_run.py:3106–3111`). N's step400_export_weights_fresh_v1 policy starts at0. Discovery's forward success would therefore not establish even N's first row plan. Discovery also lacks t.py/u.py/e.sh and returns after publishing WAITING_REVIEW.json; no training/review approval can be inferred from its exit0.

The launch uses one row per microbatch,72 microbatches per rank: pose16, VQA32, routing16, pointing8; four ranks give288 rows per optimizer step. One-GPU execution that preserves the global batch would need all288 row contributions per step and a different sampler/accumulation implementation.

One H10080GB does not fit the launch's default resident training state even at microbatch1. `full_ft.py:42–48,160–184` trains the LM, freezes vision/merger, and keeps base masters in FP32; `wrap_full_model:314–344` shards them across ranks. At world1 there is no shard reduction. State storage is approximately `4*P_base + 12*P_trainable` bytes (masters + gradients + two Adam moments), excluding heads, activations, gathers and allocator overhead: about132GB for9B base/8B trainable parameters, or144GB if all9B train. These are analytic estimates, not measured parameter counts or GPU peaks.

`C1_FSDP_CPU_OFFLOAD=1` exists (`carrier_c1_run.py:1192–1203`) and changes state placement. It does not bypass world4 or recipe/admission pins. An offloaded one-GPU fork would need host-RAM/activation measurements and would not prove the launch's four-GPU resident-state or collective behavior.

There is no valid a/b command or completion-time estimate under unchanged C. A future one-GPU implementation would need coordinated changes to recipe_for, R1 validation/planning, world admission, kit launch, and the distinction between canary identity and launch identity; it would also need CPU offload or a different state-storage implementation. A planning estimate is1–2 engineer-days for implementation plus independent review, excluding queue/staging/GPU time; no build was attempted here.

Keep any future canary's source, P export/head shards, base/tokenizer/processor files, pixel/frame layout, prepared row databases, row-plan order, removals, loss weights, trainable groups, optimizer, LR horizon, initialization and numerical dtypes byte-identical or hash-identical to the intended launch. A one-GPU serialization can preserve global row membership but cannot prove four-rank FSDP/collective behavior. Record every intentional identity difference explicitly and regenerate the affected proof/review; do not patch the sealed capsule after admission.

If four GPUs are acceptable, C already provides `r1_training.stop_after_step=3` (`r1_training.py:95–97`, `carrier_c1_run.py:2337–2338`). It retains the1000-step LR horizon and fixed milestones, checkpoints after step1, then checkpoints and exports m3 at the stop boundary because export_at_stop=true. This setting must be bound before preparation/handover/review; it is not an authorized post-admission edit. An external R1_STOP_FILE/K3 request also stops at a boundary, but a polling helper cannot guarantee exactly three steps. Neither option proves training before obtaining a four-GPU allocation.

Evidence to publish for any bounded real-training proof: exact config/source/asset/sampler identities, host/admission/review receipts, all-rank first_step_*.json, metrics for each step with finite losses/gradients and no substitutions, per-rank peak memory/timing, checkpoint_000001_<uuid>/complete.json and final checkpoint shards/optimizer/RNG/layout pins, m3/artifact.json with heads/full_weights manifests/shard hashes, disk-guard records and copier archive/generation receipts. A complete marker alone does not prove a successful reload; add a reload check if that is part of the intended claim.

Before any canary, the supplied launch kit needs its documented routing-selection arming step (`b/pl.py:20`, R1_ROUTING_SELECTION_PIN_MISSING). C also has two sequential configuration blockers across the tested scenarios: missing pixel pins in original N, then `P_EXPORT_CONFIG_DIFFERENCE:max_pixels`/`min_pixels` after the requested overlay. The concurrent fix tree was not inspected. Native check outputs are in offline_results.json, offline_more_results.json and supplemental_results.json.
