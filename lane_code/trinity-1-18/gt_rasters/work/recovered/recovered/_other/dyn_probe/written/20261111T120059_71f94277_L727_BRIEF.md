## Why (the user, 2026-11-11)
"i wonder if we also need to look at dynamic scenes for the VLA - interesting to study." and "we should preemptively develop all this code and test it! so when it's time to actually run, we don't need to debug and waste time!" Our model answers spatial questions from camera pose and depth decoded by a frozen geometry tower (G3T), a static-scene model. In robot manipulation the arm and the held object move, and in real homes people move. Before spending GPUs on dynamic training we measure, without training, how much pose and depth degrade on dynamic clips against static clips.

## Build: package work/dynprobe/ with tests, plus the data
1. Data (public, with motion-capture camera poses and sensor depth, TUM file format): the TUM RGB-D freiburg3 dynamic sequences walking_xyz, walking_static, walking_rpy, walking_halfsphere, sitting_xyz, sitting_static, sitting_halfsphere, and the static reference freiburg3_long_office_household; from Bonn RGB-D Dynamic, three dynamic sequences (a person-tracking one, a balloon one, a crowd one) and one static one. Write work/fetch_data.sh (resumable, throttled as above, sha256 of each archive recorded) and run it, staying under the 10 GB cap; if the cap binds, keep TUM complete and note which Bonn sequences are missing.
2. Loaders for the TUM format: associate rgb, depth and ground-truth pose by timestamp; build clips the way the student reads video (32 frames spread uniformly over a clip; also contiguous 32-frame windows); export each clip as frames plus poses relative to frame 1, intrinsics and depth maps. Add a loader interface for robot videos with a fixed camera and a moving arm (LIBERO agent-view frames from HDF5 demonstrations; the data arrives later from lane vla_libero, so test it on a synthetic HDF5 fixture).
3. Model runners behind one interface `predict(clip) -> poses, depths, scale`: (a) the G3T tower as the student uses it; find the entry points in the newest student code, read-only, at /scratch/jjyeung/orch_cd/integ_v3/work/tree/student_pilot/g3t_online.py and tower_read.py (and head_api.py, camera_head.py, point_depth_head.py for the student's own heads; the T0 m800 checkpoint path is in the inventory); (b) the student's own pose and depth heads; (c) a hook for a second geometry model that handles motion (pi3 or a similar public checkpoint), implemented only as far as it needs no download over 2 GB. The runners will run on a GPU later; on CPU they must run against a stub that returns ground truth plus controlled noise, and the G3T runner must at least import and build its inputs on CPU.
4. Metrics: relative rotation error in degrees and translation direction error against frame 1; trajectory error both after Sim(3) alignment and unaligned at the model's own metric scale; depth AbsRel and delta<1.25 on valid sensor pixels, overall and split into moving and static pixels (derive a moving-pixel mask by warping consecutive frames with ground-truth pose and depth and thresholding the residual; validate the mask on the static sequences, where it must be nearly empty). For the fixed-camera robot videos: the predicted camera motion, which should be zero, and the depth change on background pixels.
5. The readout, written in out/RUN_CARD.md with exact commands, expected runtime and GPU memory if the tree states them (otherwise "not measured"): dynamic against static error per model, with clip-level bootstrap intervals; the pre-registered rule from the plan (robust-pose or dynamic training earns GPUs if the student's dynamic error exceeds both 1.5 times its static error and the motion-aware model's dynamic error; if G3T fails where the student fails, the teacher is the cause); and the no-information row (identity pose, median depth). The launch script must start the run under a stall guard that reports when its output stops updating.
6. Tests on CPU (`python -m pytest work/dynprobe/tests -q`): metrics on synthetic trajectories with known errors (a known rotation gives that error; Sim(3) alignment recovers a known scale); the moving-pixel mask on a synthetic scene; loaders on a tiny synthetic TUM-format fixture and on one real downloaded sequence; an end-to-end dry run of the whole pipeline with the stub model on two real sequences, producing the readout table; resume after an interruption.
