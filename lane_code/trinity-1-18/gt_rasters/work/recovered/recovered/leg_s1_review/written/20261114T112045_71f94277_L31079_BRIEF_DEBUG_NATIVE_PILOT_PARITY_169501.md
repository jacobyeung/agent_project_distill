# Debugging: why the routed-read pilot's parity probe made no camera call (Orchard job 169501)

## Background

We are training a spatial vision-language model ("the leg", run 469ddece, a continuation of a parent model called CP1 m200). Some question types (absolute distance, room size, camera pose and motion) are answered by the model calling its own heads from inside generation; a "routed reader" serves those calls. The reader was built and accepted on Trinity against the parent, then packaged as a one-GPU job on the Orchard cluster. Its pilot is the first time the reader has executed the **leg's** weights (the step-200 export).

The pilot loaded the model (96 s, 21.6 GB), then failed at the parity gate with `ValueError: Native GPU prompt/pixel/cache/head parity failed`. P1, P2 and P3 each passed; the gate failed because `camera_call` was false: the probe's decode contained zero calls. The probe (reader file `nomdg.py`, function `run`, about lines 266-287) takes the first task's row, replaces the question with `Read the camera pose at Frame 1 using <pose frame=1>. Report the camera values.`, generates, and requires a call that starts with `<pose `. The model generated 33 tokens and stopped:

```
</think>

< frame=1>
< turn=0>
< zoom=1.000>
</ turn>
</ frame><|im_end|>
```

The spacing after `<` and `</` suggests that a token was dropped from the displayed text, or that the model emits a different grammar from the one the reader recognizes. Earlier plain-text evaluations of the same step-200 export showed that on routed question types the model emits routing calls and waits for a response.

## Question

Find the cause, with evidence at the level of tokens and code, and say what it means for the scored read (636 items: 150 distance, 36 room size, 450 camera). The candidate explanations, none of which is established:

1. **Display or tokenizer mismatch.** The generated ids include a token that the job's tokenizer decodes to an empty string (for example an added or special token that the trainer's tokenizer defines and the staged tokenizer lacks, or that is skipped on decoding), so the real output was a well-formed call that the reader's call detection then missed, either because it parses decoded text or because it looks for other token ids.
2. **Grammar drift between parent and leg.** The leg's training rows teach a different call syntax for camera reads (for example a nested program with `frame`, `turn`, `zoom`) from the `<pose frame=N>` call the reader serves, so the reader as built cannot serve this lineage's calls.
3. **Out-of-distribution probe.** The probe question is one the parent answers with a `<pose ...>` call and the leg does not, while the leg still makes recognizable calls on the real items. Then only the gate's probe is wrong.
4. Something else (a head or adapter not restored, a wrong prompt mode, a wrong chat template).
