# Refute review: out/cachefix.patch (per-instance presence in cache_for/lift)

**Verdict: APPROVE.** The patch is correct, it changes nothing on single-presence data, and no consumer is missed in a way that changes behaviour. Claim 2 misnames its callers, and deployment needs a reseal (findings 1 and 7); neither is blocking.

What I ran: `test_cachefix.py` (29 passed, 0 skipped; the K1 directory exists on this node); `patch --dry-run -p1` against the sealed A4 (applies cleanly; the patched copies match it byte for byte, sha c4ed0aa5…/39e06e65…); `review/probe_edges.py`, the full StageOne.features chain (lift, link, scene_candidates, accept_features, candidate_vectors) on unpatched vs patched modules; `review/scan_keys.py` over all 300 stored K1 caches. Logs are in `review/*.log`.

1. **Claim 2 misnames the stage-1 callers (non-blocking).** `live_parity_adapter.py:133` and `ground_sources.py:116,165` call `ofs.lift`, which is `tree/ofs/core.py:87`, a separate unpatched copy. `ground_v3.py:159` passes `O` (ofs.core) too. `price_masks.py:21` calls the K1 kit's own `linker.lift`. None of them reaches `routed_candidates.lift`, so they are unchanged trivially. In A4, the only callers of the patched `lift` are the three `cache_for` sites in finding 2. `test_stage1_caches_lifted_directly_are_unchanged` is real but tests a non-production path, and its docstring is wrong.
2. **Claim 3 holds, but its consumer list is incomplete (note).** `cache_for` has three callers in A4: `b/e2e_reader/stage1.py:134`, `routed_features.py:304`, and `h1eval/reader_core/e2e_reader/stage1.py:116`, which the claims omit. The h1eval copy has cap 100 and cross-name pools, but its `sam3_detect` also stamps one scalar presence (:82, :90), so it is unchanged. In A4, nothing serializes, hashes or iterates the keys of `cache_for` output; `lift` reads only score, mask and presence. Outside A4, `sb_kbox4/serving_reference.py:91-93` repacks `cache_for` output and feeds it to `build_tables.extract`, which calls `detections`. That function ignores instance `presence`, so the output is unchanged today, but a mixed pool sent down that route would collapse again.
3. **Claim 1 holds (confirmed).** `stage1.py:96` computes one `presence = sigmoid(presence_logit_dec).item()` per frame, and `:104` stamps it on every kept instance. The socket at `:200` always binds `sam3_detect`. Mixing comes only from `variant_cache.merge_record:20-23`, which keeps the base record presence and gives each merged instance its own `source_presence`. `sb_kbox4/predicted.py:18-21` keeps raw-name entries only and raises `raw_name_presence_mismatch`. The served-journal check in MIXING.json is indirect: `per_instance_presence_journaled` is false and the step-400 journals are missing. Claim 1 rests on the code reading, which holds.
4. **No change on single-presence data (confirmed).** On single-presence frames (157 candidates, 86 multi-member tracks), the probe found proposals, track membership, accepted ids, feature dicts and selector vectors identical. The same held with float32 presences, 0-d torch-tensor presences, and tied scores (104 candidates); NaN presences propagate identically. On real data, K1DIAG compares 7,733 candidates over 770 names: proposal digests include `p.presence`, and x, proposals, selections and boxes are all identical. That result is not vacuous.
5. **Mixed frames are now consistent (confirmed).** In the probe, the unpatched code puts the raw member mean presence (`sam_presence_members`, accept_features `:185`) outside the lifted `[presence_min, presence_max]` for 78 of 156 candidates; the patched code puts none outside. Every patched proposal carries the presence of the raw entry at its index (0 mismatches), so ordering is sound when raw lists are score-sorted, as `sam3_detect` and `cache_detect` emit them. K1DIAG agrees: 1,227 out-of-range candidates drop to 0. The 39/770 selection changes on merged pools give a −0.07 MRA contrast with a 95% CI of [−0.86, 0.70], so no measurable effect.
6. **New strictness (note).** `cache_for` now raises `KeyError` when any entry, not only the first, lacks `presence` (probe: unpatched passes, patched raises). No producer omits the key, and `accept_features:185` already requires it on every member.
7. **The sealed bundle pins both files (non-blocking, process).** `A4/src/9.json` `payload_pins` lists routed_features.py 736c5a64… and routed_candidates.py 9a200410…, and `8.py:30` raises `Helper differs` on any mismatch. Shipping the patch needs a new sealed package and an epoch launch; a patched A4 cannot be run in place.
8. **No collision with an existing instance `presence` key (confirmed).** Across 300 stored K1 caches (145,161 instances), instance keys are query, score, joint_score, box and mask, plus source_presence and source_prompt on 97,912 of them and source_query on 39,842. No instance has `presence`, and record presence is always a Python float. So `instance.get('presence', record['presence'])` cannot pick up a key with another meaning.
9. **`routed_features.detections:59-75` is a separate defect the patch leaves in place (note).** It stamps `record['presence']` on every instance and ignores K1 `source_presence`. On merged K1 caches, alias instances therefore get the raw phrase's presence. It does not matter for any served read: `b/e2e_reader` never calls it; it is reached only from `select_instances` (`live_instances314.py:127`, tree caches and the live tower, one presence each) and from `build_tables.extract:20`. The served sl118 head trains on raw-only isolated tables (`isolate_tables.py:46`, `sl_tables.raw_prompts_only:110-123`, which rewrites presence to `source_presence` and raises on a mix). It does matter for any future merged-pool table built through `extract`: those tables would still use raw presence while a patched merged-pool server used per-instance presence, a train/serve skew. Fix `detections` too before running a merged-pool experiment.
10. **Evidence caveats (note).** K1DIAG's `fixed` variant swaps both the modules and the detect function (`per_instance_detect`, without the guard), so it is not a pure patch-only A/B. It is harmless here because mixed_frames is 0 and the result is identical. `test_cachefix.py` exercises only routed_* on a stub Geo; the probe and K1DIAG cover accept_features and the vectors. `tree/ofs/core.py:113` keeps the same record-presence pattern, which is correct for its single-presence stored caches.
