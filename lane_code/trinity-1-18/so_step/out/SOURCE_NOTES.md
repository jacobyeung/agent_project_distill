Projection matmuls, sigmoid beta, FP32 decay/softplus, Q/K head replication and output projection remain native torch in all cases (`:460–467,512–521,553–560`). Missing causal-conv1d does **not** disable FLA's chunk rule, its recurrent rule or its norm. `use_cache=False` in the trainer (`T/student_pilot/carrier_c1.py:414`) means the 5k training sequence uses the chunk rule, not the token-by-token recurrent decode loop.

The torch chunk rule normalizes Q/K, transposes/contiguously copies Q/K/V/beta/g to FP32, pads to a multiple of 64, constructs chunk decay and triangular matrices, runs 63 triangular-update iterations, then carries state through `ceil(L/64)` chunks. At L=5000, that is 79 chunks and 56 padded tokens (`:259–320`). Its FP32 state has shape `[batch, value_heads, key_head_dim, value_head_dim]`. The norm fallback casts to FP32, computes mean square and reciprocal square root, multiplies the affine weight, computes SiLU of the gate and multiplies, then restores input dtype (`:193–202`). The recurrent fallback loops over sequence positions, but at the cached-decode callsite the sequence length is one.

Qwen3-Next has the same independent selection: `E/transformers/models/qwen3_next/modeling_qwen3_next.py:344–346,539–556,644–653,690–702`; its reference chunk implementation starts at `:373`. Qwen3.5 is the trainer's actual native class.

“Importable FLA” is weaker than “FLA selected.” `E/transformers/utils/import_utils.py:845–853` requires CUDA availability and FLA version >=0.2.2. `_is_package_available` at `:50–82` consults import metadata, falling back to the module's `__version__`; a namespace shadow or wrong overlay can fail the gate. The gate is cached. `is_torch_cuda_available` at `:208–213` calls `torch.cuda.is_available()`. A CPU-only probe will therefore show torch fallback even if Python can import an FLA package. An ABI/import error in an accepted package can raise during import rather than quietly select torch.

### Expected cost at 5k tokens — estimates, not measurements

Use `C = 2*key_heads*key_dim + value_heads*value_dim`. The installed text-config defaults (`E/transformers/models/qwen3_5/configuration_qwen3_5.py:77–96`) are width 4096, 32 layers, 16 key heads, 32 value heads, 128-dimensional heads. These imply C=8192. They are an arithmetic example; the kit records the actual production config before using them as a model census.

* **Convolution:** with kernel width 4, 5000*C*4 = 164 million multiply-adds per layer. One BF16 `[1,C,5000]` buffer is 81.9 MB. Separate convolution/slice/SiLU adds launches and at least one extra read/write pass. Estimated unfused forward time: 0.2–3 ms/layer; estimated removable overhead relative to a fused path: 0.1–2 ms/layer. At 24 linear layers × 72 rows × roughly two forward visits, this suggests 0.35–6.9 s/step before convolution-backward differences. These are bandwidth/launch-scale estimates, not a measured causal-conv1d speedup.
* **Torch chunk delta:** 63 triangular updates plus 79 recurrent chunks create hundreds to thousands of eager operations and autograd nodes per layer. Each FP32 `[1,32,5000,128]` Q/K/V-sized buffer is 81.9 MB. A `[1,32,79,64,64]` matrix is 41.4 MB; several such intermediates coexist, plus retained backward state. Estimated reference forward: roughly 10–100 ms/layer on H100, versus an estimated 1–8 ms for the fused chunk path; shape, kernel versions and bandwidth can move these ranges substantially. Multiplying even 10 ms by 24×72×2 gives 34.6 s before backward. The high end is incompatible with a 133-s whole step if those dimensions/layer counts apply. That consistency check makes “only convolution missing” plausible, but does not prove it.
* **Gated RMSNorm:** several FP32 elementwise passes over 20.5 million elements in this example, versus fused reads/writes. Estimated 0.1–1 ms/layer additional forward cost, or 0.35–3.5 s/step over forward plus recompute, before backward differences.

All three kernel substitutions can change floating-point reduction/fusion order. They cannot promise bit-identical losses or gradients. A candidate numerical gate is `abs(loss_on-loss_off) <= 1e-4 + 1e-3*abs(loss_off)` and per-tensor gradient relative L2 error <=1e-3, with a separate max-absolute-error report and finite checks. This is a proposed BF16 gate, **not a validated tolerance** for these kernels. The delivered scheduling/cache patches instead require exact equality in CPU tests and zero loss tolerance in the GPU timing kit.

The [official Qwen3.5 documentation](https://huggingface.co/docs/transformers/model_doc/qwen3_5) describes hybrid attention and optional kernel dependencies. The installed version's individual callsites above determine the exact fallback behavior; the generic warning does not.

## GIL and CPU-thread competition

`W = /scratch/jjyeung/orch_n30/so_step/work/tree`. The CPU producer executes Python JSON decoding, audits, processor orchestration and per-token decode callbacks (`W/student_pilot/carrier_c1_run.py:1107–1162`; `T/student_pilot/carrier_c1_data.py:43–62`). These Python sections compete with the main thread's model-launch code and Python hooks under CPython's GIL. Native kernels can release the GIL; that does not make the surrounding Python concurrent. Python documents the single-interpreter-thread restriction in [threading](https://docs.python.org/3.12/library/threading.html#threading). Installed torch binding generation illustrates GIL release around an ATen call (`E/torchgen/api/python.py:1095–1114`); the conditional binding helper distinguishes retaining and releasing it (`E/torch/include/torch/csrc/Exceptions.h:344–399`). This is not a claim that every processor/tokenizer callback releases the GIL.

Two simultaneous CPU tensor operations can each enter an OpenMP team. The installed implementation enters `#pragma omp parallel` and uses that team's thread count (`E/torch/include/ATen/ParallelOpenMP.h:16–48`). At eight intra-op threads, the main/producer pair can demand approximately sixteen runnable workers per rank, or 64 across four ranks, before communication/autograd/helper threads. This is a possible concurrency envelope, not a measured thread census; teams include their calling threads and can be idle or restricted by grain size. PyTorch explicitly warns that OpenMP need not share one intra-op pool across calling threads and recommends budgeting CPU threads to avoid oversubscription ([CPU threading](https://docs.pytorch.org/docs/2.11/notes/cpu_threading_torchscript_inference.html)).

CUDA backward normally runs on autograd device worker threads (`E/torch/autograd/grad_mode.py:312–331`; device-thread declarations at `E/torch/include/torch/csrc/autograd/engine.h:203–232`). FSDP uses default, all-gather, pre-unshard and post-backward **CUDA streams**, not one dedicated CPU thread per layer (`E/torch/distributed/fsdp/_runtime_utils.py:240–274`). Its Python hooks may execute on autograd workers and compete for the GIL. The communication backend also owns watchdog/monitor and completion-hook thread machinery (`E/torch/include/torch/csrc/distributed/c10d/ProcessGroupNCCL.hpp:1055–1070,1360–1384`). Their exact enabled count depends on the production backend/configuration; they are additional to the two CPU teams, not a known constant to add blindly.

The main thread's finite-loss scalar checks and model metric scalar reads can drain pending GPU work. A producer-induced launch delay can therefore increase full-step time even when `data_seconds` falls. The 28.2-second overlap ceiling has **no positive guaranteed lower bound**: zero gain or a slowdown is possible. The timing kit records ON/OFF per-microstep forward/backward host duration, effective intra-op/inter-op counts and thread environment. Interpret those alongside paired whole-step wall time. If host work slows, retain OFF, evaluate a lower process-wide CPU thread count in a separate matched experiment, or design a process producer with its own one-thread environment, RNG/IPC validation and the same admission boundary. Do not call `torch.set_num_threads` opportunistically inside the worker: its documented startup requirement is `E/torch/_torch_docs.py:9815–9825`, and it is not a reliable isolated worker budget.

The kits do not force eight production threads. `torchrun` supplies `OMP_NUM_THREADS=1` when the variable is absent for multiple processes (`E/torch/distributed/run.py:849–861`); the repository helper uses a default of four only when unset (`T/student_pilot/common.py:110`). Record the effective runtime count rather than assuming either default won.

## CUDA timing and the removed synchronization

An event records on its specified/current stream (`E/torch/cuda/streams.py:176–245`). The kit records events on autograd workers and chooses `_unshard`'s explicit stream (`E/torch/distributed/fsdp/_runtime_utils.py:277–309`); reduction runs inside the post-backward stream context (`:748–778,831–858`). A shared backward flag plus the current graph-task ID labels checkpoint recompute. Mocked CPU tests verify stream selection and labels; only a real CUDA run can validate elapsed values. Backward stream relationships are documented in [CUDA semantics](https://docs.pytorch.org/docs/2.11/notes/cuda.html#stream-semantics-of-backward-passes).

Before backward returns, FSDP makes the current stream wait on the post-backward stream (`E/torch/distributed/fsdp/_runtime_utils.py:1084–1108`, especially `:1099–1104`). The trainer uses no extra forward side stream. Removing its pre-forward device-wide synchronization preserves this dependency; a pending asynchronous CUDA error still surfaces at a subsequent finite-loss/scalar synchronization before the optimizer update. The likely direct gain is well under one second, still unmeasured.
