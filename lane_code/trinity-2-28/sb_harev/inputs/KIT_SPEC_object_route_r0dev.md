## 1. Question and legality
R0-dev is the reserve set registered to decide route against direct (98 ScanNet++ rooms outside every training stream; `R0_RESERVE_SCENES_20261116.md`). For each category below, does the program fed by the checkpoint's own towers (SAM 3, the selector head, tower geometry, fixed math) beat the step-200 direct answer on the same items? Every rule is fixed before this kit runs (the reader's rules, or kit 1's winner chosen on K1 train); each category gets one look; no official item is read. A second look at a category on R0-dev after a rule change is a new registration, to be asked for in a QUESTION event.

## 3. GPU pass (one 48 GB card; about 3 GPU-hours expected, hard stop at 6)
Per scene, resumable, with `DONE.json` and sha256 of each output:
1. G3T on the 32 frames of the scene's item set (about 12 s), `depth_grid` 32 x 51 x 51 and poses.
2. SAM 3 image features for the 32 frames once, then `sam3_detect` for every distinct object name in the scene's size, relative-distance, appearance-order, absolute-distance and counting items (name as written: lowercase and strip only). Store per name and frame the kept proposals (mask at the reader's 80 x 112 raster as RLE, score, presence), which is what `StageOne` consumes. Expected about 2,500 (scene, name) pairs at 2 to 7 s each.
3. Only if kit `tower_frames` Part A or B passed its bar: the same two steps on the scene's 64-frame layout, as arm `T64`.
Read frames from `/scratch` only; write under the lane folder. No 9B model is loaded.

## 4. Programs (CPU; the reader's `StageOne` with rule `candidates_argmax`, then the box rule; a `not seen` or `box unavailable` operand makes the program refuse the item)
Box rules: `today` = `lift_bestspread`; `object` = kit 1's gather and winning fusion rule, only if kit 1's first bar passed.
- **Absolute distance (290):** two grounds and `box_grid_5cm`, as the reader prints it; metres. No direct answer exists at step 200 for these items, so this row is the head's own score on unexposed ScanNet++ rooms under each box rule, reported against the constant (29.5) and against leg D0's step-200 direct read of the same items (`san_kit` root `('D0', 200)`) as context, not as a paired decision.
- **Size (293):** longest edge of the printed box, in the question's unit.
- **Relative distance (279), two-candidate check:** parse the direct trace's stated order; take the two candidates it places nearest the asked end (closest or farthest); compute the box gap from the reference object to each; answer the one the gaps favour; if any of the three grounds refuses, or the trace states no order, keep the direct answer. Also report the full program (gap to every option) for reference.
- **Appearance order (246):** the first printed frame of each named object; the option whose order equals the order of those frames; ties broken by the order in which the two objects' lowest-index proposals appear; if an object is not seen or no option matches, keep the direct answer. Report the strict program (refusal scores 0) beside it, and per object: first printed frame against `gt.first_pos_f32`, exact and within one.
- **Counting (385), diagnostic only:** the number of gathered objects for the name (`object` rule), against the truth; no decision.
Each program is scored by the item's own rule (MRA for numeric, accuracy for choice), with the scorer the direct read used.

## 5. Statistics and bars, written before any number
Paired differences head minus direct on the same items; 95% percentile bootstrap over rooms, 10,000 draws, seed 20261119; item-weighted means; ReVSI points = category points / 7 with the subtype weights of the trace analysis, section 11.
- **Size routes** if head minus direct is at least +5.0 type points with a lower bound above 0. **Stays direct** if the upper bound is below 0. Otherwise undecided, which means direct. (Run size only if kit 1's size screen passed or the `object` rule exists; with `today` alone the expected result is the 50.7 against 73.6 already measured, so report it without a decision.)
- **Relative distance, two-candidate check, routes** at +3.0 with a lower bound above 0; the check can change an answer only where the gaps disagree with the trace, so also report how many answers changed, and how many of those became right and wrong.
- **Appearance order routes** at +5.0 with a lower bound above 0 for the fallback form. Run it only if kit 1's first-seen screen passed; otherwise report the per-object first-seen rates alone.
- **Absolute distance:** no bar against direct here. The `object` rule is confirmed on unexposed rooms if it beats `today` with a paired lower bound above 0; a loss with an upper bound below 0 withdraws kit 1's PASS.
- **`T64` and `da3_f32`** are reported beside the primary arm and decide nothing in this kit.
A route verdict here licenses a build of rows and a reader read for that category; it is not a benchmark claim.

## 6. CPU dry run (before the GPU pass)
(a) Load the item file and the direct table; require every size, relative-distance and appearance item to join to exactly one direct row, and print the join counts per type. (b) Run each program end to end on two K1 captures from the stored K1 caches with made-up items of each type built from the captures' GT (size from the GT box, order from GT first-seen), to prove parsing, option matching and fallback; the appearance program on GT masks must return the GT order. (c) Parse the stated order from all 279 relative-distance traces and report how many parse; under 250 is a BLOCKER for that program. (d) One R0 scene's frames open and match `FRAMES_MANIFEST.json` sha256.
