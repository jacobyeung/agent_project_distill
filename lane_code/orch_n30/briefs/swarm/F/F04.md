# F04: analyze_read.py, a per-type failure analyzer for any slim read table

Read /data2/jjyeung/agent_project_data/distillation_orchestrator_20260918/orch_n30/briefs/swarm/SWARM_RULES.md first. It binds you, and so does the file it names first.

## Goal and why
The project builds a ~9B spatial VLM that answers from RGB and calls heads inside its own checkpoint in its chain of thought; each training boundary is judged by development reads (dev-S1, R0-dev, facing twins, routed slices). Today each read is diagnosed by hand over hours. The next leg (vehicle N) exports at steps 100 and 200 within about 12 hours; a tool that turns one read into per-type failure tables in minutes lets the orchestrator rank the next lever the same hour.

## Inputs (read-only, node-local)
- 32 slim read tables: /scratch/jjyeung/swarm_20261120/corpus/<read_id>.jsonl (165 MB in all; read them as streams, one line at a time).
- Their map: /scratch/jjyeung/swarm_20261120/CORPUS_MAP.md (line 4 lists the keys; it also holds per-read tables, per-type means, flip counts and three full example items: direct, routed with head calls, native).
- The failure taxonomy of track C, if it exists when you start: run a plain `ls /data2/jjyeung/agent_project_data/distillation_orchestrator_20260918/orch_n30/briefs/swarm/C/` (that one folder only) and read the prompt files there that define a taxonomy. If the folder does not exist, use the default taxonomy below; either way the taxonomy lives in a JSON file the tool loads, so track C can replace it without code changes.

## Default taxonomy (one primary label per arm row, first rule that fires; secondary labels allowed)
- FORMAT: parse_failed, empty answer, or answer outside the option set or not a number.
- RUNAWAY: hit_cap true or finish_reason not "stop".
- NO_CALL: a routed or native arm whose question family expects a head call but tool_calls is empty (state which families expect calls; derive it from the reads where most items call).
- CALL_ERROR: a tool call whose response is an error, a refusal, empty, or a malformed return.
- GROUNDING: the call returned but the grounded object or frames are wrong or too few (use whatever box-audit or instance keys the slim tool_calls carry; list the keys you used).
- HEAD_VALUE: the printed head value itself is far from truth (numeric families: ratio outside 0.5-2.0 to truth where the truth unit allows).
- COPY: the final answer disagrees with the value the head printed (the model did not answer from its own call).
- UNIT: answer off from truth by a unit factor (100, 1000, 0.3048, 2.54 within 5%).
- NEAR_MISS: numeric score in (0, 0.5).
- WRONG_OPTION: multiple choice, wrong letter, none of the above.
- FACING: question_type or set marks a facing-away twin and the answer flips direction.
Scores are as recorded: score >= 0.5 counts as right (CORPUS_MAP says so); report means, not only rates.

## Build
Work in /scratch/jjyeung/swarm_20261120/work/F04. Write analyze_read.py (Python 3.12 standard library only; it must run with /scratch/jjyeung/envs/p1cpu/bin/python and with plain python3.8+):
1. `analyze_read.py READ.jsonl [--taxonomy tax.json] [--arm NAME|all] [--compare OTHER.jsonl] --out DIR`. Stream the input; memory bounded by item count, not file size.
2. Outputs in DIR: SUMMARY.md (one screen: per type n, mean score, call rate, cap rate, and the top three failure labels with counts and lost points, where lost points = sum of (1 - score)); TABLE_by_type.csv; TABLE_by_type_label.csv; EXAMPLES.md (three shortest failing items per (type, label) with item_id, question, truth, answer and the 400-character trace head); with --compare, FLIPS.csv (right-to-wrong and wrong-to-right per type on common item_ids, with both labels) and a paired mean difference per type with a 10,000-draw bootstrap over rooms (seed 20261120; the `room` key).
3. Always print call rates beside scores (a project lesson: a distance gain once came from a lost call).
4. Refuse with a clear message if a line has a question_type or truth from an official benchmark set (set names containing revsi_official, vsibench_official or vsti); the tool must never be used on official items.
5. Tests (pytest, in work/F04/tests/): one fixture per label built by hand (no corpus lines copied into tests beyond what you write yourself), compare mode on two tiny fixtures, the bootstrap seed, refusal of an official set name, and a streaming test that a 50 MB synthetic file runs under 200 MB RSS.
6. Run it on every one of the 32 corpus files (nice -n 10, one at a time) and on the --compare pairs CORPUS_MAP lists for the routed dev-S1 636-item reads (s200 to s400, s400 to s544) and the direct 3120-item B2048 arm (s100 to s200, s200 to s400, s400 to s600). Record wall time per file.

## What counts as a finding
Cross-check your per-type means against CORPUS_MAP's per-type tables; any mismatch is a finding (in the tool or in the map). Also report the three largest lost-point cells (type x label) on the routed s544 read and on the direct s600 read, with example item_ids. These are development items only.

## Price
Minutes saved per read (hand analysis versus your measured wall time) and the lost points per cell, in MRA points on the named development set.

## Out of scope
