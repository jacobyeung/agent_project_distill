# F03: per-dataset tower frame count (64 for ARKit captures) as an option in served reads

Read /data2/jjyeung/agent_project_data/distillation_orchestrator_20260918/orch_n30/briefs/swarm/SWARM_RULES.md first. It binds you, and so does the file it names first.

## Goal and why
The project builds a ~9B spatial VLM that answers from RGB and calls heads inside its own checkpoint in its chain of thought; the served geometry tower (G3T) supplies depth and cameras to those calls. ARKit captures get 32 tower frames while ScanNet and ScanNet++ mostly get 64, and ARKit fails the camera rule worst (2 of 23 pass). One Orchard test found that 63 frames repaired 0 of 5 gross ARKit captures, but its decode control voided the verdict. The orchestrator wants the option built so that a controlled read can test it without new code; whether to use it is not your decision.

## Method
1. Work in /scratch/jjyeung/swarm_20261120/work/F03. Find in orchard_t1 where the tower's input frames are chosen per capture and where the count differs by dataset; quote file:line.
2. Add a config option `tower_frames: {default: <today>, arkit: <n>}` (per-dataset count), default identical to today. Extra frames come from a separate dense-frame manifest (path, sha256, frame ordinal, dataset, rotation applied) passed by flag; the reader verifies every hash before use and refuses the run when a requested frame is missing. The 32 anchor frames must stay a subset in the same order (nested), and the tower's outputs at the anchors are what the reader serves.
3. Apply the same decode and rotation path the served ARKit frames use (upscale and rotation as the record states); a 1/255 decode difference moved failing cameras by 1-18 degrees, so write a test that the extra frames go through the identical function.
4. Record the per-capture tower frame count and the manifest sha256 in every read record and in the summary.
5. Tests (CPU, synthetic frames): default parity (same frame lists and byte-identical record fields except the new ones), nested anchors, refusal on a missing or wrong-hash frame, the rotation path for Left/Up/Down captures, and the record fields.
6. Estimate the tower's extra GPU time per ARKit capture from any timing the serving code logs or a record states (the dense plan guesses about 2.5 s per 64-frame pass on an H100); label it an estimate.
7. Produce `diff -ruN` against the staged orchard_t1 copy.

## What counts as a finding
A place where the served path already decodes or rotates ARKit frames differently from training or from the tower's own expectations (file:line, the input, the wrong output).
