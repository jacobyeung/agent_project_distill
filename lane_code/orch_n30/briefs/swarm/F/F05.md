# F05: evaluation option for 64, 96 and 128 frames, with the frame layout matched to training

Read /data2/jjyeung/agent_project_data/distillation_orchestrator_20260918/orch_n30/briefs/swarm/SWARM_RULES.md first. It binds you, and so does the file it names first.

## Goal and why
The project builds a ~9B spatial VLM that answers from RGB and calls heads inside its own checkpoint in its chain of thought. The user ruled that 64 frames beat 32 and that evaluation may use 100 or more frames. A mismatch between the evaluation frame layout and the training layout has cost 3 to 13 points before, so the more-frames option must be built so that the layout is explicit, recorded and checked against the checkpoint's training layout.

## Facts you must respect (from the project's lesson record)
- f17 lineage: 32 distinct frames paired natively into 16 temporal groups ("spread"), about 2,300 visual tokens.
- T0 and carrier lineage (T0 m800, CP1): 32 frames, each duplicated to fill its own temporal pair ("duplicate"), 32 groups, about 4,160 visual tokens.
- Measured on T0 m800: dev 858 = 42.6 (32 spread) / 50.0 (32 duplicate) / 46.7 (64 nested spread). More frames is a development experiment against the trained format, never a default for an official read.
- "Nested" means the 32-frame sample is a subset of the 64-frame sample, which is a subset of the 96 and 128 samples (the CP2 kit used 64 nested VQA frames).

## Method
1. Work in /scratch/jjyeung/swarm_20261120/work/F05; copy the files you edit into work/F05/tree/ with their relative paths.
2. Add `frames.count` (32, 64, 96, 128) and `frames.layout` (spread | duplicate) to the eval config and CLI, default exactly today's behaviour. Make `sample_indices` produce nested samples: the 32-frame indices must be a subset of the 64, and so on, for every video length (including videos shorter than the count; say what happens then and refuse or pad explicitly, never silently).
3. Add a layout guard: the request names the checkpoint's training layout and count (or reads them from the export's artifact metadata if the format has them; quote where). The run refuses when the layout differs, unless `--allow-layout-mismatch` is given, and every record and the summary carry layout, count, temporal groups and visual tokens, plus `matches_training: true|false`.
4. Compute visual tokens per item for each (count, layout) with the processor arithmetic the code uses (no model download); report the context cost table, since duplicate at 128 frames may exceed the model's context.
5. Make `timing_audit` correct for the new counts (true frame timestamps are required; a project result says true frame timing matters).
6. Tests (CPU): nesting for lengths 10, 31, 32, 33, 64, 200, 5000; default byte-identical indices and packed input metadata versus the original code; the guard refusal; token arithmetic. Use /scratch/jjyeung/envs/pdtest_v1/bin/python (has torchvision; install nothing; if pytest is missing there, use unittest) for tests that import torchvision, and /scratch/jjyeung/envs/p1cpu/bin/python for the rest. Prefix with `CUDA_VISIBLE_DEVICES= OMP_NUM_THREADS=4 nice -n 10`.
7. Produce `diff -ruN` per tree.

## What counts as a finding
Any place where today's code could already run a layout different from training without saying so (file:line, the input that triggers it, and what it would record). Any frame-cache path whose key omits count or layout, so a 64-frame run could read a 32-frame cache.

## Price
Cite the measured 3 to 13 point cost of a layout mismatch for any finding that permits one; the option's own gain is unpriced until a development read at 64 frames runs.

## Out of scope
Running any model, decoding real benchmark videos, reading any official benchmark item, choosing the frame count for a read.

## Orchestrator review before landing
Default parity (indices and packed metadata), the guard, and the cache key. This changes what a read evaluates, so one independent review by the other model family is required before any read uses a non-default count.
