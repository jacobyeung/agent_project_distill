## Goal and why this task matters
We are training a ~9B spatial VLM, end to end from RGB, whose chain of thought calls heads inside its own checkpoint and answers from what they print; it must beat open 9B models on ReVSI, VSTI and VSI-Bench and later serve as a cheaper base for navigation fine-tuning. A training leg is one 24-hour Orchard job on 4 H100 that spends about 3.5 h before its first step and then reaches only about 450 steps at about 133 s a step, and the reads that judge each boundary take 4 to 6 h on one GPU slot, so every minute removed buys more steps or more experiments. At about 450 steps a leg, each second removed from the 132.6-s step adds steps for free; the older recipe spent 35-50% of its step in the torch fallback of the linear-attention layers, and job A still logs that fallback on every rank.

## Question
Where does the non-data part of N's step (about 100.9 s of 132.6 s; forward, backward, optimizer and communication are not separately measured) go, and which changes cut it without changing the math beyond bf16 rounding? Known leads to check first: carrier_c1_run.py has fla_check (3179) that runs only when the environment variable C1_EXPECT_FLA=1 (2918), and nothing in the kit appears to set it or ship the fla wheel; carrier_c1.py forces sdpa at 191 because of an additive attention bias; FSDP1 FULL_SHARD runs with backward_prefetch=None (full_ft.py near 314-345); the LM uses gradient checkpointing (carrier_c1.py near 196) although peak reserved memory is 71.9 of 80 GB; each rank runs 72 microsteps of one row (about 4.5k tokens) per step.

## Method
1. Confirm from code which linear-attention path N runs, why the fast path is off, and what enabling it needs (env switch, wheel staged into the job environment, version pins, the kit's environment manifest). Read the transformers source for the exact fallback condition.
2. Build a tiny model on CPU with the same layer types as the student (read the layer layout from the kit config k/c.json or the tree's configs; scale widths down) and use hooks and torch.utils.flop_counter to count, per microstep: vision-tower passes (frozen parts must run without autograd and only once), recompute passes, attention calls by implementation, host-device syncs (.item(), .cpu(), torch.cuda.synchronize) and optimizer work on frozen parameters.
3. Rank the levers by expected seconds per step: fla kernels for gated delta net; flash or efficient SDPA for full-attention layers with the bias expressed as a mask the efficient kernels accept; selective instead of full recompute within the memory headroom; FSDP backward prefetch and limit_all_gathers; packing 2-4 rows per microstep with cu_seqlens (fla supports varlen); torch.compile of the vision tower; removing optimizer state for frozen parameters.
4. Patch the top three behind switches with CPU parity tests (loss and every gradient equal on the tiny model, two-rank gloo where FSDP is involved), and write files/B02/gpu_bench.py: one Orchard job that times the real step with each switch ON and OFF on a fixed batch and checks loss parity.

## What counts as a finding, and its price
A finding names a lever, its code location, the evidence that the slow path runs today, the expected seconds per step with the source of the estimate, and the parity risk. Price as seconds per step x 450 steps / 3600 x 4 = GPU-hours per leg. CONFIRMED needs the code path proven on the CPU model and a passing parity test; all GPU timings stay UNMEASURED.
