## Question
What happens in a 24-hour leg, hour by hour and at its boundary, as the code behaves; what must a watcher check, and when; what does each refusal name mean; how is a resume started; and which operator steps that need an agent today could a plain shell script do?

## Method

Trace the job from `sbatch --hold` to the end of the allocation: wrapper, job.sh, b/v.py, b/pc.sh, b/x.py, then bootstrap (z.py), staging and preparation (a.py), review wait (rv.py), the train launcher (t.py) and the trainer (carrier_c1_run.py train, run_steps, checkpoint, export, stop timing at 2443-2453), the copier (pc.py, pc.sh), the live publisher (pl.py) and exit (o.py, l.py). 2. The boundary: the stop time (wall 86,400 s minus stop_before 3,600 s against TK_JOB_START), the stop checkpoint and stop export, the upload order and the 150 s reserve, the receipts that prove a clean stop, and the accepted loss if the node dies between exports.
3. The resume: the exact inputs a second job needs (stop checkpoint objects and receipts, resume_pin latest, sessions to mint for the new job id, kit state, review receipt, identity checks), the order of operator actions, what must match or the job refuses, and how to verify the step count continued.
4. Operator judgment: from the status log, the pointers and the monitor output, list every step that needs an agent's judgment today. For each, say whether a plain shell script can do it (inputs, check, action, output, how it fails safe) or why judgment stays (and the rule the human or orchestrator applies). Sketch each script in bash (sketches only; run nothing against Orchard).
5. While reading, note defects: a refusal name with no documented meaning, a phase with no witness, a watcher check that cannot fire, a timing the code contradicts, a resume input nothing produces. Each is SUSPECTED with file:line.
