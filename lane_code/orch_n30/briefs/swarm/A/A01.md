## Question
Does the trainer compute the loss the recipe intends on every row? Check, in this order:
1. Label construction: which tokens carry labels (assistant turns only; tool responses forced into the trace, i.e. `<tool_response>` blocks, must carry no label, since the model does not generate them); the one-token shift; -100 on padding, prompt, vision tokens and chat-template markers; whether the end-of-turn token is supervised.
2. Truncation: when a row exceeds the length cap, which side is cut, and can the answer or the final `<answer>` span be cut while the row still counts.
3. Loss normalization across gradient accumulation (72 microsteps per rank per step, one row per microstep, 4 ranks, global batch 288): token-mean per row then row-mean, or a global token mean? Is the division by microsteps and by world size applied exactly once? Do long-trace rows get more or less weight than the recipe says?
4. Collate and packing: attention masks, position ids (including multimodal rotary positions for video frames), any cross-row leakage if rows are packed.
5. Per-stream weights or mixing ratios that reach the loss (VQA, routing, pointing, pose streams): applied once, to the right rows.

## What counts as a finding, and its price
A finding is a code path that gives a wrong label, mask, position or weight on a concrete input, shown by a test you ran. Price it in GPU-hours per training leg (96 GPU-hours per leg) or in benchmark points on dev-S1+R0-dev (3,120 items) where you can argue the size; otherwise write "unpriced" and why. A design choice that differs from what a comment or config says is a finding only if you can show the effect on a row.
