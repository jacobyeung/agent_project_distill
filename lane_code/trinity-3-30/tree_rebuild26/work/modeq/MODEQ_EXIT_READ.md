## 3. Ranked likely causes for 173964
1. **Address-space limit, then the GPU forward.** admit sets RLIMIT_AS to 180 GiB and never restores it (s1_admission.py:139-141; no other setrlimit in carrier_c1_run, production_proof, r1_loader or r1_population). The same process later loads the model and moves it to cuda:0 (production_proof.py:173-175; carrier_c1_run.py:3088 first_batch_check). CUDA context creation under an AS limit on a 1.8 TiB host likely fails with a RuntimeError. _run catches it (:181), RESULT is REFUSE, and a.py:86 exits 1. The timing fits, because the forward is the last step after about 45 min of prepare. Exit code 1 rather than 137 fits too. The GPU path has never run: QD_STEP1.md says the tests "capture cuda:0 without accessing a GPU". The codex build transcript flagged the same limit (line 5654), unverified. Confirm: RESULT or q0.json shows a refusal like `RuntimeError:CUDA ...`, or a MemoryError traceback appears in r0.json, with steps ending at `r1_loader.production_audit`. A 1-minute test also works: in the pinned venv on an H100 node, set RLIMIT_AS to 180 GiB and run `torch.zeros(1,device='cuda')`. Note that the reservation depends on host RAM. Rule out: steps include `all_rank_full_forward`, or the refusal names a code from the tree.
2. **A named input refusal in _run** (production_proof.py:70-177: entry.py host checks, r1_rooms, r1_persisted.verify, admit or audit). Confirm by the refusal code and the last entry in steps.
3. **h.py or rv.py refuses after ADMIT** (h.py:9-42; rv.py:258-271 census). Confirm by finding N/v.json (h.py:43) without WAITING_REVIEW.
4. **Discovery-only paths.** The f0 wrapper is low risk: its signatures match carrier_c1_run.py:1240, 1393, 3020 and 3088, and its errors are swallowed (f0.py:69-75). The dr base-db substitution (pl.py:135-138) is also discovery-only.
5. **Resources, ruled out or low:** OOM kill would give 137, not 1. Check memory.events oom_kill to confirm. Disk ENOSPC is ruled out: 5123 GiB was free at staging (j2.log), and the job wrote 1.4 TB. The bwrap tmpfs (j.sh:344) is ruled out because shmem stayed about 0 (n_ops9 item 2). The last sample was at 02:00:36Z, so the final 3.5 min are unsampled. A dirty/writeback stall would slow the job, not fail it. An l.py crash is possible but unlikely.
