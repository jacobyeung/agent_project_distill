# Lane b11_native: native adapters and inputs for the official VSTI and ReVSI reads of the step-544 model (build B11; CPU only)

Read and obey `$R/orch_tools/CODEX_BUILD_COMMON_20261115.md` first.

## Why
The project trains a 9B spatial vision-language model whose routed question types (camera displacement, camera movement direction, absolute distance, room size) are answered by calls that its own heads and frozen towers serve inside the forward pass. A direct read of this model leaves those calls unserved, so only a "native" read, in which the reader serves the model's calls, gives a real benchmark score. On VSTI the closed models score 73.73 (primary) and our best direct student 69.41; our parent model's routed camera answers score 83.9 and 98.0 on the official camera items against 43.2 and 68.0 for the closed models. A single-student native VSTI read is therefore the one measured path to a headline above the closed models, and no such read exists. The planning report is `$REP`: your task is its build brief **B11** (search for the line that starts with `**B11 —`); source keys resolve in its "Source register".

The native reader itself belongs to lane `evalx` and is being resealed tonight: read `$R/evalx/STATUS.md` and the sources under `$R/evalx/work/milestone/native_package_s24_05/sources` and `$R/legs1_routed/out2`, change nothing there. Lane `official544` has already prepared the same kind of inputs for official VSI-Bench: read `$R/official544/events/20261115T0509Z_RESULT_native_inputs.md` and copy its forms (item schema, frame records, candidate phrases, geometry forecast, input report).

## Hard rule on labels
Official answers never enter a file the model-side code reads. Write every item file label-free (question, options, capture, frames, timing, routed family) and keep answers in a separate scoring file that only the scorer opens after generation. Do not print, summarize or tabulate official answers; census work uses question text and metadata only.

## Build, VSTI first, then ReVSI
1. **Inventory with hashes**: official rows and corrected labels (VSTI-450 and 5,736; ReVSI official999), the exact frames each benchmark's protocol uses and where they live, the frozen VSTI route rule (`$R/official_reads/VSTI_ROUTE_RULE_FROZEN_20261111.md`), existing dense geometry and mask caches per capture, and for each capture what is reusable, what converts on CPU, and what needs a GPU pass (name the pass, its inputs, bytes and a time estimate from recorded timings; say when the estimate is a guess). VSTI's two pose routes need dense geometry and no masks; ReVSI distance and room need open-vocabulary masks plus dense geometry on its exact frames.
2. **Inputs**: label-free item files in the native reader's schema, per-capture frame records with true frame numbers, candidate phrases where masks are used, a forecast of geometry refusals under both the sealed guard and the reviewed replacement `validate_up_convention` (`$R/rs_contracts/out/PATCH_geometry.diff`; review `$R/rc_review/out/REVIEW_VERDICT_RS_CONTRACTS.md`), and a unit census from question text.
3. **Adapter code** in your lane only: whatever the native session needs to accept these item sets (for example a pilot selection that does not assume every routed family is present, the benchmark's scorer and both VSTI aggregations), written as patches against the reader's sources with tests, for the reader's owner to adopt. Serve the model's actual calls and bounded failure recovery; no external answer selection.
4. **CPU proof**: real row decoding and tokenization on real items where frames are on this node, call dispatch through the production session with stand-ins only at the GPU boundary, frame, pose and calibration identity, refused and disabled calls, zero-filled denominators, the official scorers reproducing a known published or recorded score from an existing answer file of ours, and line coverage of the changed code.
