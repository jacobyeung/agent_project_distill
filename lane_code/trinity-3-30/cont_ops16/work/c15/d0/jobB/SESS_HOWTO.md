## Part sizes and verification

The mint tool's recorded interface takes names, not sizes. The uploader reads the finished file size `S`, calculates `step = ceil(S / 4)`, and gives part `k` offset `k * step` and length `max(0, min(step, S - k * step))` for `k=0..3`. Thus the export's byte count is not needed to generate the four names; the available record does not expose the mint script's HTTP request, so it does not independently establish every server-side initiation parameter. Source: [gcsput.py](/scratch/jjyeung/orch_n30/cont_ops/work/d0/kitfull/b/gcsput.py:70).

Each upload sends its range in one PUT with its length as `Content-Length`; success requires HTTP 200/201 and matching server size and MD5. Receipts record the name, offset, length, hashes and generation; matching name, size and offset cause a later invocation to skip that part. The four objects restore by concatenation in part order. Sources: [upload and validation](/scratch/jjyeung/orch_n30/cont_ops/work/d0/kitfull/b/gcsput.py:19), [receipts and skip](/scratch/jjyeung/orch_n30/cont_ops/work/d0/kitfull/b/gcsput.py:57), [restore](/scratch/jjyeung/orch_n30/cont_ops/work/d0/kitfull/b/gcsput.py:7).

The recovered facts describe a no-payload status check: issue a zero-length PUT to the private session URI with `Content-Range: bytes */OBJECT_SIZE`. HTTP 308 indicates an incomplete session; 200/201 indicates completion. The record explicitly describes documented behavior, not an observed check of the 469ddece sessions. Use the known part size as `OBJECT_SIZE`; do not print or log the URI. Source: [status behavior](/scratch/jjyeung/orch_n30/cont_ops/work/rb/recovered/orchard_cp2/results/20261113T203136_71f94277_L24885_result.txt:29). The separate Orchard HTTPS probe uploaded 65,536 bytes using its own session; it did not verify a production session without uploading. Source: [probe result](/scratch/jjyeung/orch_n30/cont_ops/work/rb/recovered/leg_s1_tree/commands/20261113T145436_71f94277_L22161_cmd.sh:3).
