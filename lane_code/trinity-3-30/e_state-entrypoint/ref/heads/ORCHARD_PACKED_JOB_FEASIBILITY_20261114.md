# Orchard packed-job feasibility — 2026-11-14

## Decision
- The question is whether one four-GPU advanced job should run the step-200, step-400 and final evaluation reads plus the IF-P0 baseline as four independent one-GPU steps.
- The answer is **NOT BUILT**. Two owner admissions, new seals and confirmations, namespace/configuration fixes, a controller, a step shim and a joint review cost more than the expected one-to-four-hour queue gain; only an Orchard run could establish the proposed isolation.
- ORCH instead plans an ordinary one-GPU P0 job on advanced after the production allocation releases the cap. Its kit needs a partition allowlist, not a step mode; general serves the three evaluation reads in sequence.
- Packing is worth building for many short one-GPU jobs over days, with step identity, isolation and bounded returns designed into the kits from the start.

## Candidate controller, not launch authority
- The candidate uses independent staging. Three 16-CPU/200-GiB evaluation steps plus one 8-CPU/200-GiB P0 step consume 56 CPUs/800 GiB; 64 CPUs/832 GiB leave control headroom within the stated 208-CPU/1.8-TB node. QoS admission remains unproved.
- The outer request would be `/usr/local/bin/sbatch --parsable --account=mt01 --partition=advanced --nodes=1 --ntasks=1 --gres=gpu:4 --cpus-per-task=64 --mem=832G --time=24:00:00 --signal=B:USR1@300 --no-requeue --output=/dev/null --error=/dev/null --chdir=/tmp --job-name="a15_cot_ap${TOKEN}"`.
- Each evaluation step would use `/usr/local/bin/srun --jobid="$SLURM_JOB_ID" --nodes=1 --ntasks=1 --exact --exclusive --gres=gpu:1 --gpu-bind=single:1 --cpus-per-task=16 --mem=200G --time=06:00:00 --immediate=60 --kill-on-bad-exit=0 /usr/bin/python3 -I -s -B -S "$C/step.py" --packet "$PACKET" --limit-seconds 21600`.
- P0 would use `/usr/local/bin/srun --jobid="$SLURM_JOB_ID" --nodes=1 --ntasks=1 --exact --exclusive --gres=gpu:1 --gpu-bind=single:1 --cpus-per-task=8 --mem=200G --time=12:00:00 --immediate=60 --kill-on-bad-exit=0 /usr/bin/python3 -I -s -B -S "$C/step.py" --packet "$PACKET" --limit-seconds 43200`.
- C and step.py denote unbuilt controller assets. A readiness barrier would verify distinct step IDs/UUIDs and effective resource scopes before heavy work; each shim would run newly confirmed owner BATCH bytes unchanged and expose one UUID as CUDA device 0.
- The controller would never write into worker folders. It would signal a worker parent at D-300 seconds, escalate only that step at D-120/D-60, preserve other returns, and relay the outer warning to all active steps. Host OOM/storage failure is a common failure, not isolated by this design.
