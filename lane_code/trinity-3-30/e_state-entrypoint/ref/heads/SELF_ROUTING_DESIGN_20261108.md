## 1. Recommended design (settings)

### 1.1 Mechanics: one renderer, teacher forcing in training, a routing decode loop at inference

| Item | Setting |
|---|---|
| Sequence | Native Qwen3.5 template, thinking on. Video, then 32 carriers (C1 placement = config parameter; C1-b default), then the question, then `<think>\n` + target. Carriers precede the question, so head readouts are question-independent in both training and inference. |
| Routing tokens | Dedicated tokenizer tokens for the five head openers `<depth_at` `<move` `<pose` `<turn` `<box_3d` (v3.9 adds `<turn`); arguments are ordinary text (`frame=12 pts=[[512,760],[530,700]]>`); `<tool_response>` `</tool_response>` are Qwen's native special tokens. Initialize each new token's input AND output embedding row to the mean of the embeddings of its plain-text tokenization (`<`, `depth`, `_at`), so step-0 logits are sensible; the rows train with the LM (full FT). Calculator calls (`<dist`, `<closest`, `<cam_dist`, `<angle`, `<turn from=P at=P to=P>`, `<area`) stay plain text and are detected by regex on the decoded tail; dispatch head-`<turn` vs calculator-`<turn` on `at=`/P-labels (v3.9 rule). |
| Training (teacher forcing) | The whole target is one teacher-forced sequence. Labels: -100 on the prompt, on every `<tool_response>...</tool_response>` block including both delimiters, and on padding; loss 1 on plan, prose, routing openers, arguments, calculator commands, decisions, unit lines and the final answer. Spans come from derivgen's `tool_output_spans` through `carrier_c1_routing.suffix_mask` (token-exact; a straddling token refuses the row). Never mask by number regex. Loss per row = token mean of supervised tokens (as `CarrierC1.forward` does now); the per-stream recipe weight for `routing` is 1.0. |
| Inference (`generate`) | A manual decode loop (new `carrier_c1_decode.py`, below), not `transformers.generate`: prefill once with carriers; capture the final-layer carrier states and the private depth encoder's grids during that prefill; run the pose head once (32 poses + gravity + FoV slots 7:9) and keep them for the whole generation. Each sampled token is appended to the decoded text; when the tail closes a call (`>` after an opener token, or a calculator regex match), parse it with `p3_grammar.parse`, compute the response with the SAME `OwnGeometry` / `PrintedPointRegistry` code the trainer uses for own-valued rows, tokenize `<tool_response>` + text + `</tool_response>` alone, append those ids as forced tokens (never predicted, never scored), keep the KV / recurrent cache, continue. Invalid call -> typed error response `<tool_response>error: bad_frame ...</tool_response>` and continue; count it. Stop at EOS or the context limit; no cap below 16,384; never manufacture an answer. |
| Parity proof | Tokenizing a response alone equals its slice in the whole-suffix tokenization because both ends are special tokens; `build_routing_stream` asserts this for every row (reject on mismatch). Canary C2 (section 3) re-derives every injected response offline from the exported heads and requires byte equality, and compares the inference-time pose readout with the training-time `readout` stream output on the same video (prefix-only vs full prompt) to <= 1e-3. |
| Printed values (one formatter) | SPEC 6.2 as implemented in `OwnGeometry`: camera and f1 coordinates 2 decimals in metres (public y up), spread 2 decimals, move components signed 2 decimals + fixed-layer `distance` 2 decimals, yaw and turn whole signed degrees wrapped to (-180, 180], calculator dot/cross 4 decimals and theta whole degrees, `cm = 0.97 * 100 = 97` written by the LM. Angles never get decimals (pose error ~13 deg). Thresholds (`>= 135`, spread limits 0.25 / 0.10 near the border) are evaluated on the printed, rounded numbers in training and at inference. Frames are 1-based numbers only; no seconds. Head layout `per_frame`: the asked frame is used directly and `image_frame=` is refused (C1 has a carrier per frame). |
| FoV | Exactly one FoV, the pose head's slots 7:9 (detached), feeds both the depth head's conditioning and the unprojection, in training (`pose_fov`, `readout_heads`) and in the decode loop. No fixed prior. |
| Gravity | The pose head's gravity branch trains in the final/mixed mode (weight_gravity 1.0 inside the camera loss; pose-only's `weight_gravity=0` must not carry over). `OwnGeometry` must refuse `up=None` in production rows instead of falling back to camera -y. |

### 1.2 Value source during training: GT and own heads, per head, gated by measured head accuracy

Own values are produced online (never from a bank): for a row drawn for own values, one no-grad prefix forward (`prefix_batch`: video + carriers) reads pose, gravity, FoV and the depth stencils of every click in the row (`depth_queries`, `query_tensor`), `rerender` recomputes every head response AND every calculator response from the printed points, and the training forward runs on the re-rendered suffix (`encode_own` / `splice`). Model-authored text stays verbatim; the answer label follows the **faithful** policy (the program's decision on the printed values), never the GT label when the two differ. If re-rendering refuses (RenderError, CalculatorError), train the GT-valued row and count the refusal by reason.

| Head | Own-value gate (identical on every rank: an all-reduced 2-flag tensor per step) | Probability once open |
|---|---|---|
| Depth (`depth_at`, `box_3d`) | Open when the depth head is initialized from the Stage-1 V-C artifact (AbsRel 0.159) AND the pose-stream FoV error EMA(100 steps) < 2 deg (FoV feeds the unprojection). Without a Stage-1 init: EMA depth AbsRel on the pose stream < 0.25. | p = 0.5 |
