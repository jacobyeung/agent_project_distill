Question: How can pySpatial and SpatialClaw timing use additional RTX 6000 Ada cards on trinity-0-13 while preserving native execution, question identity, timing clocks and source integrity?

Answer: Each launch uses a complete immutable package copy with its own manifest, seal and fresh RAM root. Native inputs, workers, serializers, scorers and four question slots remain pinned. pySpatial uses code LOW and answer/fallback MEDIUM. SpatialClaw Pro uses its released default HIGH planner; Flash uses explicit HIGH. SpatialClaw's helper retains provider-default MEDIUM.

Placement: Dependencies, static inputs, packages and outputs live on node-local RAM under `/dev/shm/jjyeung/timed_fanout_1112`, with the pinned local SAM3 checkpoint and moving-scene frames. The corrected SpatialClaw environment is `/dev/shm/jjyeung/spatialclaw_envfix_1112/release_v1`; its complete 44,432-entry dependency manifest is pinned. pySpatial uses the existing 43,423-entry local source closure without modifying it. Cross-node copies use one reused InfiniBand connection, one tar stream at a time, with no credential transfer. Every Python process and probe uses `-B` and `PYTHONDONTWRITEBYTECODE=1`.

Ownership and concurrency: The launcher assigns each physical card after its owner releases it. A clear-card observation grants no allocation. Each queue accepts a card argument, holds its per-card runner lock and claims rows under the `QUEUE.txt` inode flock. Native canonical leases and the shared per-card timing-window lock prevent concurrent timing work on the same card. Four workers per card can overlap provider traffic across allocated cards and accuracy cells under the authorized policy.

Admission: The package verifies all question assets, native seals, model files and dependency hashes. Service startup requires the exact RTX 6000 Ada model, at least 45,000 MiB free, fewer than 128 MiB used, less than 10% utilization and no compute or graphics process. Each unit waits for 90 continuous clear seconds, resets after a busy sample, and rechecks its private port. Startup and these waits remain outside question clocks.

Storage: All units preserve 110 GB free scratch. Retained caps and free RAM margins are 12+5 GB for pySpatial STI/ReSTI, 20+5 GB for its complete OSI retry, 40+10 GB for its static 150-question variant, 4+5 GB for each SpatialClaw moving-scene unit, and 8+30 GB for each independent static SpatialClaw unit or the Flash aggregate. Dispatch guards enforce the remaining output budget and margin.

Measured capacity: The OSI evidence root retains 12.195 GB with 43 authenticated merit rows and one infrastructure row; its complete 50-question projection is about 13.46 GB. The authorized retry uses a fresh root and retry2 selection record and reuses no rows. The static pySpatial follow-up retains 14.483 GB with 58 arrays and 54 authenticated result records, projecting about 37.94 GB for 150 questions against its 40 GB cap. SpatialClaw's observed moving-scene output is 128 MB for 23 authenticated rows; the published static retention basis is 1.581 GB for 150 questions. These are storage measurements and projections, not benchmark claims.

Visualization gate: Every corrected SpatialClaw unit needs a real SAM3 mask passed to native `PerFrameMask.visualize`, its observed shape/dtype and a returned image. The launcher retains the trace and image with hashes in a per-unit audit. The static and Flash mergers validate this evidence before publishing. The launcher and plot reviewer enforce the same requirement for moving-scene points.

Migration and claims: The source helper takes the source `QUEUE.txt` flock, proves the target rows unstarted and uncached, preserves the inode and line numbers, and writes equal-length tombstones. Committed receipts enable the destination. Current corrected attempts and Flash need no additional source edit. Failed rows, roots and selection records remain intact; an authorized complete retry has a distinct identity. Only `pyspatial_queue_v2` is live for pySpatial.

Options rejected: Legacy dependency paths could activate an unsupported queue. Bulk scratch placement would consume the required free-space floor. Editing a sealed package would break provenance. Deleting source rows would shift state markers; renaming a locked queue would separate readers across inodes. Checking only `.started` would miss a cached row. Reusing failed OSI rows would change the authorized complete trial. Averaging unit medians would not reproduce the pooled question-level clock.

Failure detection: Manifest drift, unexpected source files, changed model bytes and mismatched question membership refuse admission. Capacity, card and port guards stop or wait before dispatch. Native loading and real-input self-tests run before provider work. Missing or invalid visualization evidence prevents audited publication. Failed commands consume their reservation and retain outputs; no automatic retry or cleanup occurs. RAM artifacts must be archived before reboot or storage release.

Evidence: `NEEDS_LAUNCHER_TIMED_FANOUT.md` names the current packages, queues, point paths and commands. Each READY receipt pins its descriptor and admission/native proofs. Queue, capacity, port, clear-card, lease, native-chain, pooling and audit-validation proofs run offline. The retention audits authenticate result and trace hashes while reading only file metadata for geometry.

Status: All eleven current queue entries are READY_OFFLINE across nine immutable packages, covering 750 planned question executions. Flash HIGH passes all 150 admissions, three native per-benchmark proofs, policy checks and audit-evidence validation. The launcher owns production execution and real-input audits. This lane has made zero provider calls and zero GPU workloads and has not edited an active production queue.
