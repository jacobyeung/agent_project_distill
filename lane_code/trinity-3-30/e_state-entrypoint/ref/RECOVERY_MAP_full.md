Status: complete 2026-11-15 ~17:30Z (lane recover_map2, trinity-3-30). Listings only; no rebuild started, no copy made except a 49 MB read of the Devin sessions database into the lane folder.

## Question

trinity-2-18 went down at 10:00Z with every lane folder (`/scratch/jjyeung/orch_cd`), and trinity-2-28 stopped accepting logins at about 16:15Z. For each queued experiment and build, which inputs survive elsewhere, and what is the cheapest restart?

## Answer

The model state survives, and most of the work built on it does not. Google Cloud Storage holds every LEG-S1 export (steps 1, 50, 100, 200, 400 and 544), and Orchard holds slot A, the direct reader, its runtimes, the videos, the official questions and the raw returns of every accepted read. Two restarts can therefore begin at once: the official VSI-Bench direct read of step 544, which lane evalx27 is already rebuilding, and the ReVSI direct read once that kit exists. The rest of the queue must be rebuilt, or exists only on 2-18. That covers the native routed candidate C7, the stacked seal's tree (`tree_r1`), its rows (`rows_r3`) and grammar, the R2 contract patches, K1's rules file and GT rasters, and the reviews. trinity-1-18 holds a partial code mirror with three useful pieces: the LEG-S1 base tree, the native package s24_05 sources, and 93 GT rasters. No session store holds the bytes of any file a lane wrote on 2-18: Codex homes and Devin session databases lived on 2-18's own disk.

## Options considered and rejected

- Replaying lane-written files from session stores. Codex homes of the distillation dispatches were on 2-18's disk; the Devin CLI logs on NFS keep commands, not outputs, and the shared Devin sessions.db holds no session after 2026-09-23. Heredoc writes visible in the Devin logs can restore small text files a lane wrote with `cat > f <<EOF`, but not files written by Codex or by editors, and not tool outputs. None of the K1 files was written that way.
- Re-registering K1_RULES.json under a new hash. Not needed: the kit's own writer on trinity-1-18 (`kit_k1a/work/preregister.py`, serializing `k1_report.RULES`) regenerates the file byte for byte, sha256 cb0aadee89c86e3db41c33d450eee6d7f58558d63f56d3d189e744277ad23269 (815 bytes), equal to the pre-registration's pin; lanes k1_ops3 and k1_rules confirmed it independently on 2026-11-15 (`distillation_orchestrator_20260918/orch_n30/events/k1_rules/`). RUNCARD_K1.md and PROOFS.md are not hash-pinned; only their existence is checked.
- Staging the native read on trinity-0-28. It saves the Orchard queue, but it pushes 0-28 below the 200 GB rule and needs a GCS pull of 21.6 GB.

## What might not work and how we would notice

- The 1-18 LEG-S1 tree may be an earlier pass than seal 38917ea5. Recomputing the seal with its own source_seal.py shows this before any build starts.
- None of the 14 GCS code tars may be C7, and the newest may predate guard fixes. Comparing each tar's pins against the pin-audit record shows which build it is.
- The Orchard returns may lack per-item fields that the packet SUMMARY needs. Regenerating step 544's summary first and comparing it with the numbers in memory `result-legs1-m100-20261114` shows this.
- The 1-8 RAM disk and its `orch_cd` link may be archived and removed by the mover's default (lane mover_relief_n18_1115, default from 16:30Z). It holds only 11-10 material, so little is at risk, but the T0 m800 weights there (`mdg_build/work/data/t0mind`, 21 GB) also sit on Mind.

## Ranked restarts (benchmark value per hour of work)

1. Official VSI-Bench direct read of step 544 (row 1a): the only number comparable with f17's 63.79 and the bars; about 4 h of build and review, about 1.2 H100-h; lane evalx27 owns it.
2. ReVSI direct read (row 1b): reuses the chain runner and scorer from 1, about 2 h more; it measures the diagnosed +5.15 direction gap on the claim order's second benchmark.
3. K1 (row 3): the GT rasters and a new rules registration take 3 to 5 h of CPU work, then 3 to 6 GPU-h. It unlocks P2 to P8 and every routed official read, and it decides the selector refit that ReVSI and VSTI mask reads need.
4. Native routed read C7 (rows 2a and 2c): 4 to 6 h of build plus rehearsal from the GCS code tars and the s24_05 sources. The VSTI camera routes may run before P8; this path is the only measured one above the closed models on VSTI.
5. Packet regeneration from the Orchard returns (row 9): under 1 h per step. It earns no new points, but it restores the evidence behind the dev-S1 decisions and the continuation question.

The stacked seal (rows 5a to 5d) carries the largest eventual gain (about +2 VSI points from repairs, plus the GF-1 upside), but it costs about two days of rebuild and review before any GPU use, so it ranks below these five per hour.
