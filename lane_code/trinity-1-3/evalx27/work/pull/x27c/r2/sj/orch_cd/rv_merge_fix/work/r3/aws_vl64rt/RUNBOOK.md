The kit runs native full-weight models with vLLM 0.32.0. Each GPU owns one engine. A job runs its cells sequentially. Defaults are eight GPUs, greedy decoding, thinking enabled, and a 16,384-token generation cap. The context limit is 49,152 tokens.

The parent supplies `inputs/MODELS.json`, following `inputs/MODELS.example.json`. Example digests are placeholders and cannot authorize a live job. A snapshot entry needs an absolute directory and a pinned JSON manifest with `files: [{path, sha256, bytes}, ...]`. Paths are relative to the snapshot. Include the complete weights, config, tokenizer, and chat template. An archive entry needs its absolute path and SHA-256. The archive must contain one native safetensors or pytorch_model weight directory. The loader supplies missing config/tokenizer files from the base snapshot and validates shard indexes. It excludes the base weight index when filling metadata.

Presets:

- `E11c`: base spread and duplicate; VSI-500 plus VSTI-450 v3 in each cell.
- `P4`: base duplicate, P0.5, and P0.2; both benchmarks in each cell.
- `references`: base and f17 spread; VSI-500 plus ReVSI in each cell. `--include-ft-x` adds FT-X only when its pin exists.
- `custom`: `--cells FILE` supplies a JSON list of `{model, layout, benchmarks}`. This supports any additional pinned native full-weight export and `official5130`. `--slice N --seed S` selects a reproducible stratified official subset.

Every cell checks 16 prompt-ID sequences and two pixel/grid tensors before ordinary generation. The trainer functions are copied verbatim into a minimal dependency closure; full originals and their hashes ship in the audit archive. vLLM's returned prompt IDs must equal the trainer's `training_text` plus `encode_frames` IDs. Pixel checks use vLLM's registered HF processor, the exact request kwargs, and the trainer's tensors. If registry access fails, the report records the ordinary HF comparison and keeps numbers gated. All item scoring continues after parity failures.

Before any vLLM worker starts, the job authenticates and unpacks the pinned trainer Python 3.12 environment into its node-local `/tmp` directory. Its PyAV interpreter decodes every requested benchmark/layout cell using the evaluator decoder, with one task per CPU and shared video/layout results. The stage writes lossless RGB PNGs and an index that pins each item’s receipt, frame paths and hashes, exact indices, FPS, total frames, and realized gaps. Workers verify the index, receipts, PNG hashes, and original NumPy pixel digest before using PIL arrays for generation and trainer parity. Workers never open source videos or import PyAV. Frame-stage failures remain per-item errors that gate scores. The stage log is node-local `2.log`.

Spread uses the official two-pass PyAV decoder and floor-uniform 32 anchors. Duplicate repeats each anchor consecutively. Paired layouts interleave anchors with the nearest source frame at the requested gap, using a backward partner at the recording end. Reports retain requested and realized gaps, exact metadata, and fallback anchors. The trainer reference rejects backward partners; CPU verification compares valid forward pairs exactly and tests the requested end fallback separately.

Custom spread cells on `vsi500`, `devrows`, and `vsi500_slice` accept `frames: 64`. Without `frame_set`, they use floor-uniform 64 anchors. With `frame_set: "nested"`, they retain the official 32 anchors and add 32 indices by bisecting the largest consecutive gap, choosing the earliest gap on ties and flooring each midpoint. Nested item records include `anchor_slots`, the zero-based positions of the original 32 anchors in the sorted 64-frame input. Videos with fewer than 64 decoded frames produce per-item errors. The grid files `inputs/cells_grid{,_base,_t0}.json` use greedy decoding, thinking, and the default 16,384-token generation cap; devrows requires `--dev-rows`.

ReVSI uses its own exact 32-frame MP4s, its official source-frame-index table, and the 452-item membership. Its compact video rate preserves source duration; metadata reconstructs source FPS as compact FPS times source frame count divided by 32. The pinned source indices determine timestamps. The vendor's `ReVSIMetric.update` and `compute` remain unchanged. An offline state shim supplies tensor accumulators, and a local loader supplies GT without datasets downloads. Reports include all seven categories and the visible_32 subscore.

The parent must check AWS presence of the 213 videos in `inputs/REVSI_PUSH_FILES.json`. That list gives each exact source path, relative destination, and byte count; total 260,800,735 bytes. Push one archive through the approved parent transport, then unpack to the `--revsi-video-root` directory. The metadata and source-index table already ship in the kit. The original 32-frame GT sidecar with digest prefix `66e0175d` remains a required external pin for eligible ReVSI scores: supply `--revsi-sidecar /AWS/PATH@FULL_SHA256`. Without it, the parquet-derived GT produces provisional scores marked `do not count`. Paired ReVSI needs separately pinned source recordings and is rejected by this binder.

Outputs live at the opaque output path in `DESTINATIONS.json`, under the numeric cell index. `gR.jsonl` journals raw generations, token IDs, answers, scores, cap hits, 4,096-token rescoring, and media audits. `pR_JOB.json` holds parity evidence. `items_JOB.jsonl` merges per-item records, and `summary_JOB.json` reports benchmark aggregates, task/type scores, parse failures, empty thinks, cap counts, and number eligibility. Worker tracebacks stay in node-local `/tmp`, outside Slurm output.

Resume with an unchanged request/source/model binding and `--output` set to the previous opaque output path. Use the same GPU count. Completed items are skipped across new attempts; errors regenerate; every attempt repeats parity. A partial final JSONL line is retained and ignored. A worker failure still produces a gated merge. Smoke jobs use `--gpus 1 --smoke-items 16`; their scores are diagnostic and remain gated.

The parent runs the bind, seal, push, deploy, and submit commands in `BUILD_NOTES.md`. The shipping surface contains opaque Slurm names and paths, two authenticated archives, and a resource authorization file. The approved anonymity gate scans the sealed stage and archive member names. Deployment accepts an existing root containing only `m/`, `o/`, `.retained/`, and the deployed `b/`, `k/`, and `SHA256SUMS.txt`; it moves deployed files into `.retained/<ns>/` and preserves model manifests and outputs. Submission refuses an existing allocation for the deployment, skips CPU-only GRES rows, records the opaque-name GPU count without a name-count refusal, passes the explicit account, partition, and QoS, and appends one `evalx` submission receipt to the shared ledger. The parent checks its GPU budget before submitting. Control commands never retry failed connections. The CPU build executes none of these remote actions.
