# Counting, totals, appearance-order and first-seen rows from GT visibility (b12_cntapp, 2026-11-16)

**Question.** Can ground-truth instance rasters at each row's own 32 pins supply frame-tied counting and appearance-order rows at the scale brief 12 asks (30,000+ each), and in what form?

**Answer.** The full set (packet PACKET_b12_v2, 31,522 rows from 3,048 scenes: 2,186 D0 v5 pool scenes plus 1,038 extension frame-map scenes, minus exclusions) gives 2,113 new single-category counting rows, 8,158 totals, 14,171 appearance-order rows and 7,080 first-seen rows. Single-category counting cannot reach 30,000 without repeats: only about 0.7 new (scene, category) pairs per scene pass the gates once D0's own pairs (rows_a2's retrace) are removed. Totals carry the counting volume. Appearance order is capped at 40 per scene; the cap is a parameter, and 80 would give about 25,000. Proposed share of a 128-row VQA step: single counting 10 (D0/rows_a2 retraced plus these), totals 4, appearance 16 (with D0's 13,622), first-seen 3 as a perception row outside the 30.

**Rules.** Visible: raster pixel share >= 0.002 at 240x320 (rows_a2 calibration: first-seen equal on 433/447 pool instances). Category: not structural; in the D0 or VSI-Bench vocabulary of its dataset; no sibling label sharing its head noun or plural; no frame, unit or digit word in the label; plural labels skipped for counting and first-seen. Rooms: K1 held-out rooms (b05 TEACHER_K1 4d4736cf, 53 captures) are filtered into a separate file (48 of the 263 K1 scenes) and R0 reserve rooms (R0_ROOMS.txt bdb5d402) are dropped (0 found); ARKit room = 3dod visit_id. Missing pin: a pin whose raster has no depth anywhere (ARKit pose gaps; 104 of 159 K1 ARKit captures miss 1 to 4 pins). Counting: n >= 2, every instance visible in some pin, and every pin before each cited frame present; pairs already in D0 stay with rows_a2's retrace. Totals: 2-3 categories with disjoint words, n >= 1 each, one with n >= 2, sum <= 30. Appearance: 4 categories with disjoint words, clean onsets (no instance share >= 0.0005 in any earlier pin), first-seen pins pairwise >= 2 apart, not a D0 set; options are the true order plus 3 random permutations, letter position by hash. First-seen: clean onset. Onsets also need every earlier pin present.

**Form.** Counting keeps the D0/rows_a2 list form, one list item per instance at its first-seen frame plus a coarse region (left, middle, right of the instance's mask centroid), then the count. Per-instance "Locate:" lines fail the validator above five instances (number provenance), so they were rejected. Appearance keeps the D0 form unchanged (first-seen frame per object, then the order).

**What might not work, and how we notice.** GT annotations can miss instances, so a visible but unannotated object makes the GT count too low; the error swarm on counting reads would show over-counts concentrated on these rows. ARKit rasters use annotated boxes lifted from sensor depth, which can mark box-adjacent pixels as the object. Same-frame instances with the same region word are indistinguishable in the trace. The 0.002 floor may count a sliver the student cannot recognise. 64-frame rows need 64-pin rasters (b2.py and build_t1_cr.py are 32-pin; the ARKit reader fetched depth at 32 pins only).

**Tests that would settle it.** A refute review of the visibility rule on SAMPLES_30.md against the RGB frames; a small SFT dose (counting + totals vs D0 retrace only) read on ReVSI count single/total and VSI-Bench counting.
