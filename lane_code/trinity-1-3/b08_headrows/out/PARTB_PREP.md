## Built (CPU, tested)
- `code/headrows/assign.py` (177c4765...): one decision per training item from the deployed pipeline's response; the module docstring states the rule. In short: head only when status is exactly 'ok', the answer is right (numeric within 15% of a positive GT in Decimal arithmetic; counts and option letters as exact strings, as `ground_rows.validate` compares them), every operand's accepted instance ids equal its non-empty GT ids (no duplicates, no 'unmatched', no extra operands), and the Session record that `ground_rows.pack` consumes binds to that answer. Direct when wrong or masks mismatch or GT ids are missing. Recovery only for the runtime's own '<name>: not seen' status with a record holding it. Drop otherwise (ineligible identity, room/appearance order, size/direction easy, operator fault, missing or unknown status, bad provenance, unusable record, non-positive GT). Any non-head decision leaves the item on its current form.

2. GT instance ids per operand on those items (rasters / pool instances; rows_a2 builds rasters on trinity-1-3). Without them every item lands on direct (`mask_unverified`).

4. Tree amendment (tree lane plus one independent review). The sealed validator `trace_grammar.py` a41ba191 is type-agnostic: a program-form row passes in any type, so it needs a type gate, not a lexical change. The real refusal sits in `carrier_c1_routing.py` (build loop near line 880): every policy in `POLICIES` puts a type in route OR direct, and a direct-policy row with calls is refused (`direct_policy_row_has_tool_calls`); route types drop their direct rows. The mix needs a policy with a `both` set (counting, size, relative distance, direction e/m/h, absolute distance) that keeps both forms, and a validator type gate that admits program form only in route or both types.

## Renderer and grammar coverage (read from the sealed tree copy `rows_rebuild/work/tree/src`)
- Head-form rows need no new renderer. The sealed `student_pilot/ground_rows.pack(record, provenance)` turns a v3.12-3.14 Session record (`qid, type, question, options, answer, gt_answer, candidate_id, spec_version, events[{call, response}], suffix`) into a derivgen-row-v2 route row with masked response spans, and `ground_rows.validate` re-renders it. So a head row is the reader's own recorded suffix on a training item that passed `assign.decide`.
- Grammar covers: absolute distance, relative distance, direction medium and hard (`trace_format/ground_v312.py` TYPES: `<ground>`, `<gap>`), counting and appearance order (`ground_v313.py` instance path). Not covered: object size and direction easy. Under the ORCH both-path ruling those two keep their current form until a grammar and head exist for them.
- Requirement on the response cache (brief 04 reader / brief 05 head): save the full Session record per item (fields above, plus per-operand accepted instance ids and the pipeline sha256), not only the answer; otherwise rows cannot be packed.
- `ground_rows.validate` requires `gt_accepted True`, `gt_agrees True`, `not_seen` false; recovery rows (real failure) therefore need a recovery form outside `ground_rows` (trace ruling 2.4 recovery family); tree_rebuild4 joins.
- `code/headrows/mask_match.py` (+ tests/test_mask_match.py, 3 tests): offline match of accepted masks to GT instances on the rows_a2 / K1 raster format (npz `inst`, `ids`, `labels`, `frame_indices`): GT ids per operand by normalised label (as derivgen `generate_v313` and rows_a2 `retrace.py` do), each accepted candidate matched to the GT instance with the highest pixel-summed IoU over its frames, IoU >= 0.5, else `unmatched`. The sealed pipeline's `gt_agrees` checks the answer only, so this is the mask half of the head-row rule. The cache must therefore also store accepted masks per candidate and frame (RLE is fine).

## Spec for tree_rebuild4: the `both` policy set and the validator type gate (ORCH 1250Z: I draft, tree_rebuild4 implements, one independent review)
1. `carrier_c1_routing.POLICIES` gains one policy (name e.g. `both-path-20261116`) with three disjoint sets: `route` = camera displacement, camera movement direction, camera rotation; `both` = object_abs_distance, absolute_distance_object, object_counting, object_rel_distance, relative_distance_object, object_rel_direction_medium, object_rel_direction_hard; `direct` = every other type in ALL_TYPES (object size, direction easy, room size, route planning, appearance order until brief 11, and the rest). The union equals ALL_TYPES; a type in two sets raises at import.
2. `build_routing_stream`: for a `both` type, `kind` is taken from the row (`routing.category` = 'route' when the row has tool spans, 'direct' when it has none) and both are admitted; `direct_policy_row_has_tool_calls` still refuses a direct-category row with calls; a `both` route row must carry provenance fields `pipeline`, `pipeline_sha256` and `assignment` = 'head' (from `assign.py`'s SELECTED.jsonl), else it is refused `both_row_without_assignment`.
3. The route-table config derived from the policy must not drop the direct VQA rows of `both` types (today a routed type drops them); route types keep today's behaviour.
4. Validator type gate (new pinned wrapper around `trace_grammar.validate_row`, not an edit of a41ba191): form 'program' is admitted only when the row's type is in `route` or `both`; form 'program' in a `direct` type is a new violation `program_form_in_direct_type`; form 'direct' in a `route` type is refused unless it is a recovery row (trace ruling 2.4 recovery family). Tests: a counting program row passes, a size program row fails, a direction-easy program row fails, a counting direct row passes.
5. Per-type head share is printed by the kit at preparation and at every read (greedy call rate per type), so the minority stays near 2,000 rows per type and the call rate on direct-majority types can be checked against 10%.
6. No prompt flag; the model chooses per item from the data.
