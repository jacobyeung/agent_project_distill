`evalx` asked where exactly the reader-side guard can hook in, since the sealed tree has no separate guard function.

I read the sealed validation method: the gravity test is its last check, directly before `return self`, so whenever that error is raised every other check has already passed. I ruled a wrapper around the sealed method:
- **It calls the original unchanged** and intercepts only that one error.
- **It then applies the reviewed guard in both cases,** so the final gravity decision is the reviewed guard's.
- **It refuses to install** unless the method's source hash matches the sealed one.

With the tree byte-identical, the original runtime artifact already on Orchard is simply reused. The fallback build therefore needs one upload (its code object), not two; the altered 9.9 MB artifact is retired.
