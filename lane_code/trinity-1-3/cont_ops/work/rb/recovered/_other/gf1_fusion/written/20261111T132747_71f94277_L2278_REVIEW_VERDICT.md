# Cross-family review of the GF-1 fusion connector (Claude Opus, 2026-11-11): RUN AFTER FIXES

All paths are under work/tree_gf1/student_pilot unless stated. Findings are ordered by the damage they would do to a training run.

1. **Blocker: no video row encodes at the configured 64 dense frames.** `carrier_c1_data.py:177` calls `native_square_518(arrays)` on the dense clip, and `g3t_online.py:366` raises unless there are exactly 32 frames. Final-mode `fetch` (`carrier_c1_run.py:1164-1182`) catches the error, substitutes rows and then skips; `skip_guard` aborts after about 100 microsteps. The test hides this because it patches `native_square_518` out (`tests/test_gf1_contracts.py:45`). Fix: take the frame count from `dense_frames`, and add a test that encodes a 64-frame row without the patch.
2. **Blocker: init refuses from any trained GXC checkpoint.** `gf1_config.py` forces `input=NATIVE_INPUT`, so the camera tokens come from 64 native frames with pose9 normalised over all 64. The current final GXC was trained on 32 student-unpatchified frames (`validate_arm` requires INPUT, `g3t_online.py:~150`). `check_camera_context` (`gf1.py:292-301`) therefore raises whenever the donor's camera connector is nonzero. The refusal is correct. The step-0 identity test does not cover this: it toggles `geometry_online` on the same tiny model with a zero GXC connector (`tests/test_gf1.py:1227-1238` of the patch) and never compares against the base-tree code path. ORCHESTRATOR RULING: keep the camera-token path on its trained 32-frame student input (a second tower pass under no_grad), so that step-0 outputs from a trained checkpoint are bit-identical; the dense bank for the connector may use the native dense frames.
3. **Silent cold connector in Stage 2.** `bind` copies the source `init_artifact` unchanged, and `init_from_artifact` loads `gf1` only if the heads list names it (`carrier_c1_run.py:777-782, 808`). If the Stage-1 export plus `'gf1'` is not set by hand, Stage 2 trains a zero connector with no error. Fix: in `bind`, for stage 2, require `'gf1' in heads` and a donor that carries `gf1`, or an explicit `gf1_init: zero`.
4. **Row substitution silently reshapes the data mix.** Rows without `geometry_dense`, or with a failed nesting check, are swapped for neighbouring rows, and substitutions do not count toward `skip_guard`. Fix: require 100% dense coverage in the prepare receipt, or count GF1-cause substitutions as fatal.
5. **Routed head outputs change.** `share_head_tower` (`gf1.py:316-330`) permanently replaces the routed tower's FP32 aggregator and camera heads with the GX encoder's modules, which are BF16-quantised when `encoder_dtype=bf16` (`g3t_online.py:180-184`). Pose and depth then no longer match the measured routed programs, and no parity test exists; the three live checks were skipped. Fix: keep the tower's FP32 modules and hand GF-1 a cloned bank, or prove head parity before and after the swap with a test.
6. **The evaluation path is untested.** Nothing reloads an export through the evaluator's loader with its init spec. An evaluator that lists only `pose, frame_embeddings, depth` would score the model with a zero connector. Benchmark batches also need dense clips, which no eval builder (`benchmark_eval/`, `orchard_eval/`) produces.
7. **Guards and configs.**
   - `bind` removes `fail_fast` and `admission` and sets `gate_stop=False` (`gf1_config.py:29-33`). `patch_delta_ratio` is only logged, so nothing stops a connector that swamps the RGB tokens (Stage 1 runs at an assumed 1e-4 under Adam on a 1024x4096 matrix). Fix: an automatic stop if the ratio exceeds 0.5 or the step-1 loss exceeds 1.02x the step-0 loss.
   - Config keys never read: stage-2 `gf1.learning_rate` (the code uses LM LR x `lm_lr_scale`, `gf1.py:189`), `lm_frames`, `stall_seconds`, `startup_seconds`.
   - Stage 1 is locked to world size 1 (`carrier_c1_sweep.py:64-66`), while the plan budgets 4 cards.
   - The pre-launch card's "+1.5 GO" rule describes a standalone arm; the plan reads Stage 1 only as a harm screen inside the stacked leg.
8. **Memory.** At 32 LM / 64 dense frames the shape estimates fit (Stage 1 35.5 GiB on a 48 GB card, Stage 2 64.2 GiB on an 80 GB card). 128 LM frames (82.2 GiB) is the first configuration over an 80 GB card; 96 frames leaves about 4 GiB, and the estimate excludes the hybrid-attention state and the routed tower's peak. The carrier supports only 32 LM frames today.

Missing tests that would catch the most damage:
- (a) an unpatched 64-frame row encoded end to end, with a one-hot bank impulse traced to its video token on a non-square frame (the real 37x37 to 10x13 grid with letterbox padding, through the visual hook into input_ids order);
- (b) real-checkpoint step-0 logits, base tree against the GF-1 tree, on one real row;
- (c) an export round trip through the evaluator's loader that asserts the `gf1` tensors and logits match and fails closed when `gf1` is missing.
Also not exercised: real FSDP and `average_adapter_gradients`.

Checked and correct: patch registration order (row-major tower patches, xyxy ROI on the 1024 raster, merged order t, h/2, w/2, nested index_select on bank and ROI); exact identity of the zero output under BF16; no tower gradient; Stage-1 parameter groups hold only `gf1`; ranks build identical modules; connector weights and optimizer state are saved in rank shards and heads.pt; the stall guard fires after startup and kills only its own group; unknown `gf1` keys are refused.
