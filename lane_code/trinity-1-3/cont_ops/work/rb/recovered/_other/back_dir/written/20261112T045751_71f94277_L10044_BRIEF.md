# back_dir (Codex, implement): training and dev rows for direction questions asked while facing AWAY from the reference object

Lane folder (your only writable place): /scratch/jjyeung/orch_cd/back_dir. CPU only. No GPU, ssh, git or network. Never run a command that deletes or moves files. Do not read or write /home or /data*; run Python only as `/scratch/jjyeung/envs/p1cpu/bin/python -I -s`. Other lanes' folders are read-only: copy code you change into work/. Keep new files under 2 GB.

## Why
Our student answers relative-direction questions of the form "standing by A and facing B, is C to my left, right or back?" well (85 to 93% on one benchmark's forward items) but fails the same question asked while "facing in the opposite direction of B": on 26 of 33 such items both of our checkpoints give the answer rotated by 180 degrees. Its reasoning text even says "facing away from B" and then computes the bearing as if facing B. Evidence: /scratch/jjyeung/orch_cd/evalx/events/20261112T0456Z_RESULT_backward_direction_diagnosis.md (read it whole). None of our training rows uses the facing-away wording, because the released training data and the other benchmarks only ask the facing-toward form. The fix is supervision: rows whose question faces away, with ground-truth answers and reasoning that applies the reversal.

- The pool builder that renders our current direction rows from ground-truth 3D annotations, in both forms the student is trained on (a short program trace that calls the student's own tools, and a direct answer): /scratch/jjyeung/orch_cd/dose_pool (STATUS.md; work/dosepool/*.py; the renderers under work/v314r2, work/v314r3, work/v314r4; out/POOL_S1 with MANIFEST.md, the final pool of the next training leg; out/ROWS_READ_*.md with sample rows). The runtime that executes programs in the student tree (frozen; do not change it): the archive named in the newest /scratch/jjyeung/orch_cd/leg_s1_tree/events/*_NOTE_tree_frozen.md.

## Build
1. A renderer for the facing-away variant of each relative-direction row kind the pool has (easy, medium, hard), from the SAME ground-truth geometry and the same row sources as the existing forward rows: the question says the observer faces the opposite direction of F (use two or three natural wordings, including "facing in the opposite direction of" and "facing away from"; state the wording shares and keep the option sets and their shuffling exactly as the forward rows do), and the answer is computed from geometry with the facing vector negated, never by string-rotating a forward answer. As an independent check, the answer must equal the forward row's answer rotated by 180 degrees wherever the forward row exists; report the agreement count and print every exception.
2. Both training forms, matching the forward rows' conventions byte for byte except for the reversal: (a) the program trace: it must run unchanged in the frozen runtime, so do NOT add a new tool attribute; call the existing angle tool with facing F and then state the reversal explicitly in the reasoning (the observer faces away from F, so the bearing is the tool's bearing plus 180 degrees, wrapped to the tool's range), then map the bearing to the option by the same quadrant rule the forward trace uses. Show that the frozen runtime executes the program lines of 200 hash-chosen rows and that the final answers follow from the returned bearings under the stated rule. (b) the direct form (empty think block plus the answer), as the pool's direct rows have it.
3. Row population: every training-side scene the forward direction rows cover, minus the two exclusion lists, with the forward rows' own admission gates where they apply (state which gates cannot apply to a new wording and what replaces them). Counts per row kind, per dataset and per form. Answer-letter balance must match the forward rows' balance (report both distributions).
4. Dev rows: 150 facing-away items (50 per kind where available) on the held-out dev scenes, chosen by a hash of the forward item id, with ground-truth labels by the same geometric rule, in the format the dev adapter reads, so that the weakness can be measured legally before and after training. Do not touch the existing fixed item list; write a separate list with its sha256.
5. Tests (CPU): geometry (facing away equals facing toward rotated by 180 degrees on synthetic layouts, including the boundary cases of the quadrant rule), no excluded scene in any training row, no dev scene in any training row and no training scene in the dev list, forms identical to forward rows except for the documented differences (diff a forward row against its facing-away twin), determinism of the hash selection, schema validity against the frozen tree's reader for both forms.
6. Read your own rows: paste 12 complete rows (4 per kind; both forms) in out/ROWS_READ_BACKDIR.md, chosen by hash, and say in one line each whether the reasoning is correct and natural.
