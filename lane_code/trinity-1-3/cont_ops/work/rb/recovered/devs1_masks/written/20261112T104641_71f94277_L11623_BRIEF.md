## Why
Our student answers some spatial question types better through a short program that fuses its geometry tower's depth and pose with object masks, and others better directly. Which types to route was decided on a public benchmark's test scenes, which is not a legal place to decide it. On our held-out development set (dev-S1) we already have, per question: the checkpoint's direct answers (/scratch/jjyeung/orch_cd/devs1_direct/out/r5 and /scratch/jjyeung/orch_cd/evalx/work/merge_r5) and the program's answers with ground-truth masks under tower geometry (/scratch/jjyeung/orch_cd/devs1_price/out: PRICE_DEVS1.md, per-item jsonl, the runner and its tests). The missing piece is the masks the deployed system would really use: an open-vocabulary segmenter's candidates on each frame plus our learned selector that accepts, rejects and merges them. With those, the same pricing gives the deployable program score per type, and "route this type if the program beats direct with its paired interval above zero" becomes a decision made legally on held-out scenes. Mask quality is our binding constraint, so this table is the most decision-relevant number we lack.

## Build
1. A kit that, on one GPU, caches the segmenter's candidates for every object name the dev questions need on the 152 captures' plan frames, in the same format and at the same density settings the selector was trained and priced with (read the selector lane to learn exactly which; state them), with a manifest, per-capture journal, resume, a disk estimate, a stall guard and a first-minute self-check; everything that can be proven without a GPU proven on CPU (frame ids, prompts, output schema on a stub backend, refusal cases). Say what must be staged on the run host and how large it is.
2. The CPU step after it: the selector applied to the cached candidates (its frozen accept threshold and merge rule; no retraining on dev), the programs priced with those masks under tower pose and the tower's own depth with the frozen fusion policy (reuse the pricing runner), per item, for every type the programs cover.
3. The route-table tool: per question type and per dataset, direct (the checkpoint's journal) against deployable program (same items), paired difference with a 95% bootstrap interval over physical rooms (10,000 draws), the rule's verdict (route, direct, or undecided when the interval spans zero), and the loss decomposition against ground-truth masks (wrong object accepted, object never proposed, fewer frames) as the selector lane defines it. Test the tool now on the ground-truth-mask results standing in for predicted masks, and on synthetic inputs built to produce each verdict.
4. One operator run card: stage, launch, expected GPU time, the CPU commands, the output files.
